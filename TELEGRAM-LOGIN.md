# Вход через Telegram

В версии 0.11 добавлен вход/регистрация по Telegram для сайта и браузерной PWA через официальный OpenID Connect. При первом входе создаётся отдельный аккаунт Волны; повторный вход открывает тот же аккаунт. Старые логины и пароли работают как прежде. Совпадение имени или логина не привязывает Telegram к уже существующей учётной записи.

## Подключить бота

1. Откройте Telegram и создайте бота через `@BotFather` командой `/newbot`. Выберите название и username. Бот представляет кнопку авторизации; бот не получает историю переписки.
2. В настройках созданного бота откройте **Login Widget**. Добавьте разрешённые адреса:
   - `https://volna.lknet.ru`
   - `https://volna.lknet.ru/api/auth/telegram/callback`
3. Скопируйте показанные там **Client ID** и **Client Secret**.
4. На VPS, в файле `.env` проекта, задайте:

   ```env
   TELEGRAM_CLIENT_ID=значение_Client_ID
   TELEGRAM_CLIENT_SECRET=значение_Client_Secret
   PUBLIC_BASE_URL=https://volna.lknet.ru
   TELEGRAM_REDIRECT_URI=https://volna.lknet.ru/api/auth/telegram/callback
   ```

   Секрет храните только в `.env` на сервере. Не вставляйте его в переписку, исходники или клиентскую сборку.

5. Выполните `sh scripts/update.sh`. После запуска сервера обновите страницу через Ctrl+F5. Если переменные не заданы, вход по паролю продолжает работать, а Telegram-кнопка скрыта.

## Данные профиля

При авторизации запрашиваются `openid profile phone`. Из подписанного ID token Волна сохраняет только поля, которые Telegram фактически предоставил: имя, отдельные имя и фамилию, username, ссылку на фото, ID (если он есть), а также телефон и признак подтверждения номера после согласия пользователя. Фото и публичные поля доступны другим вошедшим пользователям Волны. Номер телефона и технические идентификаторы видны только владельцу. Если согласие на телефон не дано, поле остаётся пустым. Повторный вход обновляет эти данные; изменённые вручную имя и описание в Волне сохраняются. Ссылка на фото может перестать работать со временем; тогда показываются инициалы. Telegram OIDC не выдаёт биографию, историю сообщений, контакты или произвольные настройки аккаунта.

## Прокси для запросов к Telegram

Если серверу недоступен прямой выход в сеть, можно задать `TELEGRAM_PROXY_URL` в `.env`:

```env
TELEGRAM_PROXY_URL=http://LOGIN:PASSWORD@wg-router:8118
```

Укажите свои учётные данные, не публикуйте их. В этой сборке через прокси идут только запросы сервера к `oauth.telegram.org`; запросы push и другой трафик не перенаправляются. Для `wg-router` сервер подключается к общей сети `wg-socks-mtproto-v4_default`; `wg-router` должен иметь DNS-имя в этой сети и принимать HTTP-прокси-соединения на порту 8118. Адрес `127.0.0.1` внутри контейнера указывает на сам контейнер, а не на соседний `wg-router`.

## Как работает вход

Используется OIDC Authorization Code Flow с PKCE, случайными `state` и `nonce`, браузерной HttpOnly/Secure cookie, проверкой RS256 подписи Telegram, issuer/audience/срока действия. Короткоживущий код после callback меняется на сессию один раз и удаляется. Telegram-идентификатор хранится в базе с уникальным индексом; старая база расширяется без удаления сообщений и аккаунтов.

Для привязки Telegram к аккаунту, который уже создан паролем, требуется отдельная явная функция привязки после авторизации этим паролем. Автоматически объединять записи по имени или логину небезопасно, поэтому текущая версия создаёт отдельный аккаунт.

Сайт и браузерная PWA завершают вход на веб-странице. Нативное Android-приложение начинает тот же state/PKCE-процесс с параметром `client=native`. После проверки Telegram сервер возвращает одноразовый код в `volna://auth`; приложение обменивает код на короткоживущий серверный токен. Redirect URL зафиксирован в серверном коде, OAuth-код действует один раз. Официальная документация: https://core.telegram.org/bots/telegram-login

## Если config включён, но вход не проходит

Ответ `{"enabled":true}` подтверждает наличие настроек на сервере. Правильность Client Secret и доступность Telegram проверяются при самой авторизации. Начните новый вход с главной страницы; одноразовую callback-ссылку повторно не используйте. Сразу после попытки выполните:

```sh
docker compose logs --tail=80 server
```

Строки `[telegram-login]` содержат этап и безопасный код ошибки без секретов и токенов. `token_http_400` и `token_http_401` требуют проверить Client ID/Secret и точный callback URL Login Widget. `jwks_http_503`, `jwks_invalid_json` и `jwks_invalid_payload` означают сбой получения ключей подписи. `UND_ERR_CONNECT_TIMEOUT`, `ECONNRESET` или `ERR_PROXY_TUNNEL` показывают сетевой сбой; запросы к token endpoint и JWKS используют `TELEGRAM_PROXY_URL`, если он задан. Bot API token не заменяет Client Secret.

В 0.11.28 сетевые ошибки и ошибки JWKS имеют собственные сообщения; они больше не показываются как отсутствие настройки.

## Проверка `jwks_invalid_json` в 0.11.29

Эта ошибка означает, что тело ответа с ключами не удалось прочитать как JSON. По одной строке нельзя установить, сжат ли ответ, пришла ли HTML-страница или тело пустое. В 0.11.29 исправлена распаковка gzip/deflate/Brotli в HTTP-прокси и добавлены метаданные ответа в журнал. Для проверки из работающего контейнера выполните:

```sh
docker compose exec -T server node server/check-telegram-jwks.mjs
```

Команда обращается только к публичному `https://oauth.telegram.org/.well-known/jwks.json` через настроенный `TELEGRAM_PROXY_URL`; без прокси используется прямое соединение. Client Secret для проверки не требуется. Пример успешного ответа:

```json
{"ok":true,"via":"proxy","status":200,"type":"application/json","encoding":"identity","wireBytes":430,"bytes":430,"body":"json","keys":1,"rsaKeys":1}
```

Размер и число ключей в реальном ответе могут отличаться. `"body":"html"` означает, что получена страница вместо ключей; `"body":"empty"` — пустой ответ; `jwks_response_decode_failed` — повреждённое сжатие. При HTTP-ошибке вывод содержит статус, при сетевой — код. Тело ответа и учётные данные прокси не печатаются. Исправление обработки сжатия само по себе не устраняет HTML-страницу или отсутствие выхода через прокси. Получение ключей проверяет транспорт и формат ответа; полный вход дополнительно проверяет подписанный токен.
