# Волна 0.12.107 — SDP отправляется после готовности relay

Последний журнал 0.12.106 показал конкретное зависание: получатель принял звонок, получил два relay-кандидата примерно за 0,4 секунды сбора ICE, но продолжал ждать завершения остальных сетевых попыток. Первый answer не был отправлен. Вызов завершился примерно через 9 секунд после принятия, пока клиент оставался на этапе `gather`. У звонящего кандидаты тоже появились раньше окончания сбора: около 0,35 секунды против примерно 4 секунд ожидания полного завершения.

В Android, Web и Windows изменено условие завершения ожидания ICE:

- Если есть хотя бы один relay-кандидат и число кандидатов не менялось 200 мс, клиент отправляет текущий SDP.
- Появление дополнительного relay-кандидата заново отсчитывает короткий интервал стабилизации.
- Полное завершение сбора по-прежнему позволяет отправить SDP сразу.
- При отсутствии relay сохраняется прежний предел ожидания 10 секунд и штатное восстановление. Закрытый звонок не продолжает ожидание.

Сам сбор не прерывается: отсутствие общего события завершения ICE перестаёт блокировать отправку SDP, когда relay уже готов. Поздние кандидаты не добавляются в уже отправленный SDP; штатное ICE-восстановление остаётся доступно. Общий BUNDLE-транспорт, предварительный пул кандидатов, TURN-only и UDP/TCP адреса TURN сохранены. Время фактического соединения на телефонах нужно подтвердить следующим вызовом; 200 мс — окно стабилизации кандидатов, а не обещанное полное время соединения.

В `rtc.gathered` добавлено поле `gather_exit`: `relay_ready`, `complete`, `timeout` или `peer_closed` (Web). По нему и `elapsed_ms` видно, почему клиент перестал ждать. IP-адреса, SDP и учётные данные в диагностические записи не добавляются.

## Обновление

Из `/root/volna-messenger`, где есть `.env` и `compose.yaml`:

```sh
( set -eu; test -f compose.yaml && test -f .env; volna_update_dir=$(mktemp -d); trap 'rm -rf "$volna_update_dir"' EXIT; git clone --depth 1 --branch v0.12.107 https://github.com/andluk87/volna.git "$volna_update_dir/source"; git -C "$volna_update_dir/source" archive --output="$volna_update_dir/source.tar" HEAD; sh "$volna_update_dir/source/scripts/backup.sh"; if [ -d android-native/app/src ]; then mkdir -p backups; volna_source_backup=$(mktemp -d "$PWD/backups/android-source-0.12.107-XXXXXXXX"); mv android-native/app/src "$volna_source_backup/src"; fi; tar -xf "$volna_update_dir/source.tar" -C .; VOLNA_BUILD_NETWORK=host sh scripts/build-clients.sh )
```

Установите **Android 0.12.107 (12107) на оба телефона**. Если сейчас требуется только Android, замените в команде `sh scripts/build-clients.sh` на `sh scripts/build-android.sh`. Для Windows нужен новый клиент, Web перезагрузите после публикации. Существующие настройки, данные и артефакты сохраняются; перед обновлением создаётся резервная копия. Windows-builder требует 4 ГБ свободного места.

После теста пришлите действующую ссылку на журнал из меню бота → `/calllog`. Проверим время `rtc.gathered`, отправку первого answer и время от принятия до соединения.

## Проверки

Прошли 272 Node-теста и 243 Android-теста. Собраны Web, Windows renderer и APK; проверена версия 0.12.107 (12107).

Проверяется сценарий из журнала: relay готов, а полное завершение ICE не приходит. В тесте SDP становится готов к отправке после короткой стабилизации, не ожидая десятисекундного предела. Дополнительно проверяются новые кандидаты в окне стабилизации, отсутствие relay, закрытый peer, отсутствие утечки адресов, Android-политика ожидания, общие API-тесты, Web/Windows интерфейс и сборки клиентов. Физическая сеть пользователя в среде сборки недоступна.
