# Volna: переход с SQLite на PostgreSQL 17

Сервер хранит аккаунты, сессии, переписки, контакты, настройки, очередь push и журнал администратора в PostgreSQL. Формат HTTP/SSE API сохранён; пересборка Android, Web и Windows для переноса БД не требуется. Файлы по-прежнему находятся в прежнем `chat-data:/data/uploads`. Новый том `postgres-data` содержит PostgreSQL и не заменяет том файлов.

## Существующая установка

Запускайте из **прежней папки проекта**, с прежними `.env`, именем Compose-проекта и томами. Перед запуском сохраните копию `.env` отдельно: в ней находятся SMS/TURN-настройки и пароль PostgreSQL. Нужны Docker Compose v2 и Python 3.

После получения этих исходников выполните:

```sh
sh scripts/migrate-postgres.sh
```

Если для сборок используется сеть хоста:

```sh
VOLNA_BUILD_NETWORK=host sh scripts/migrate-postgres.sh
```

Скрипт выполняет следующие действия:

1. Добавляет отсутствующий `POSTGRES_PASSWORD` в `.env` (64 случайных шестнадцатеричных символа), сохраняя остальные настройки.
2. Собирает серверный образ с PostgreSQL-клиентом, делает резервную копию старого тома, затем останавливает API.
3. Запускает PostgreSQL 17 во внутренней Docker-сети. Порт БД на хост не публикуется.
4. Проверяет целостность SQLite и внешние ключи; переносит таблицы, строки, ограничения, индексы и верхние значения последовательностей. Сверяет содержимое каждой таблицы, а не только число строк.
5. Фиксирует перенос одной транзакцией и запускает API с проверкой здоровья.

Исходная `/data/volna.db`, её WAL/SHM и файлы не удаляются. При ошибке импорт откатывается; скрипт оставляет API остановленным, чтобы исключить запись в неподходящую базу. Повторный импорт в непустую PostgreSQL запрещён. Старую SQLite нельзя считать текущей резервной копией после начала работы PostgreSQL.

Перенос сохраняет идентификаторы, хеши сессий, настройки SMS, секреты контактов и пользовательские данные. Вход старых установленных клиентов продолжает использовать прежние сессии до их обычного истечения. Установка до телефонной авторизации требует отдельного предварительного обновления старой версии; эта миграция не выполняет сброс аккаунтов.

Если перенос прошёл, но проверка запуска API завершилась ошибкой, исправьте указанную причину и выполните `docker compose up -d server`, не повторяя импорт. При HTTPS используйте также `-f compose.yaml -f compose.https.yaml`.

Не выполняйте `docker compose down -v`: это удаляет данные обоих томов.

## Новая установка

Создайте `.env` из примера и задайте пароль:

```sh
cp .env.example .env
python3 -c 'import secrets; print(secrets.token_hex(32))'
```

Запишите результат в `POSTGRES_PASSWORD` и настройте прочие параметры. Затем используйте обычный запуск Compose. Сервер создаёт PostgreSQL-схему автоматически только для новой установки. Если найдена прежняя SQLite без отметки успешного переноса, запуск прекращается с требованием миграции.

## Запуск без Docker

Нужны Node.js 24+, PostgreSQL 17 и `pg_dump` 17 в PATH. Создайте отдельную пустую БД и роль с правом создавать таблицы, функции и триггеры в её схеме. Задайте `DATABASE_URL` средствами окружения, не добавляя пароль в Git или журналы.

```sh
npm ci
# При переносе остановите все старые процессы сервера и сначала сделайте backup:
node scripts/migrate-postgres.mjs /absolute/path/to/volna.db
# Сохраните прежний путь к файлам:
export UPLOAD_PATH=/absolute/path/to/uploads
npm start
```

Значение `DATABASE_URL` имеет вид `postgresql://USER:PASSWORD@HOST:5432/DATABASE`; специальные символы должны быть URL-кодированы. TLS настраивается параметрами подключения PostgreSQL; проверку сертификатов не отключайте. `DB_PATH` теперь нужен только для обнаружения прежнего SQLite-файла. Действующая БД выбирается через `DATABASE_URL`.

## Резервное копирование и восстановление

```sh
sh scripts/backup.sh
```

Скрипт останавливает API, сохраняет `volna.dump` в формате `pg_dump --format=custom` вместе с прежним `/data` и запускает прежний контейнер обратно. Успех выводится только после создания полного архива. Сохранённый SQLite в архиве является историческим источником, а актуальные данные находятся в `volna.dump`.

Копия из панели администратора также содержит `volna.dump` и `uploads/`. Экспорт использует PostgreSQL snapshot; жёсткие ссылки удерживают неизменяемые файлы, относящиеся к этому снимку. Ошибка чтения файла или дампа прерывает создание копии.

Для восстановления остановите API, распакуйте выбранный архив в отдельную закрытую папку, восстановите `uploads/` в прежний файловый том и загрузите дамп в **новую пустую БД**:

```sh
pg_restore --exit-on-error --single-transaction --no-owner --no-privileges \
  --dbname="$RESTORE_DATABASE_URL" /path/to/volna.dump
```

Затем направьте `DATABASE_URL` на восстановленную БД и запустите сервер. Для стандартного Compose имя БД и роль — `volna`; восстановление через `docker compose exec -T postgres pg_restore -U volna -d NEW_EMPTY_DB --exit-on-error --single-transaction --no-owner --no-privileges < /path/to/volna.dump`. Сначала создайте `NEW_EMPTY_DB`; переключение стандартного Compose на другое имя требует соответствующего изменения URL. Не восстанавливайте дамп поверх работающей базы. Для полного восстановления также сохраните `.env`, настройки прокси и ключ подписи Android отдельно.

Откат к старому SQLite допустим только до первых записей в PostgreSQL. Потребуются прежние исходники/образ и прежний том `chat-data`; простое переключение после новых сообщений потеряет эти сообщения. При неудаче импорта прежний остановленный контейнер можно запустить через `docker start CONTAINER_ID`, пока он не заменён командой Compose.

## Проверки разработки

Используйте отдельную тестовую БД и роль с правом создавать схемы:

```sh
export VOLNA_TEST_DATABASE_URL=postgresql://USER:PASSWORD@127.0.0.1:5432/volna_test
npm test
```

Каждый `:memory:` fixture получает свою PostgreSQL-схему; fixtures с путём сохраняют схему между перезапусками. Тесты миграции создают синтетический SQLite-источник. Тесты резервного копирования требуют `pg_dump` в PATH. Тестовые схемы остаются в выделенной тестовой БД для диагностики; удаляйте или пересоздавайте эту БД после прогона. Никогда не указывайте рабочую БД в `VOLNA_TEST_DATABASE_URL`.

## Границы текущего перехода

Это переход хранения на настоящий PostgreSQL с прежними синхронными контрактами серверных модулей. Драйвер `pg` работает в отдельном worker-потоке; операции ожидаются синхронно, одно подключение обслуживает основной процесс. Слой SQL адаптирует оставшийся внутренний синтаксис запросов. Это позволяет сохранить существующие обработчики и целостность их транзакций, но не даёт преимущества асинхронного пула по пропускной способности.

Продолжайте запускать один API-процесс: SSE-подписки и активные звонки пока находятся в его памяти. Следующий этап масштабирования — асинхронный доступ к БД и вынос общего realtime-состояния. Bot API и исполнение hosted-ботов этим переносом не добавляются.
