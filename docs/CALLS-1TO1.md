# Звонки 1:1 — выпуски 0.12.87–0.12.88

Объём согласован с пользователем: сначала надёжные звонки 1:1 из Telegram_Calls_Technical_Spec_RU.pdf. Группы/SFU, групповое E2EE, handoff, iOS и запись в этот выпуск не входят. Существующие голос, двустороннее видео, камера, демонстрация, маршруты звука, Android Telecom/foreground service, входящие уведомления и история сохранены.

## Обязательный TURN с 0.12.88

По запросу владельца все звонки теперь только через TURN. Сервер возвращает `relay_only:true`, `relay_required:true` в privacy, `iceTransportPolicy:relay` в config; старые выключенные предпочтения не влияют на политику. Поле `relay_only` в POST оставлено совместимым со старыми запросами, но false игнорируется. На новых Android/Web/Windows relay закреплён при создании PeerConnection даже при подключении к старому API с policy=all. Выключателя в новых клиентах нет. Для гарантированного нового поведения обновляются оба клиента; уже идущие звонки нужно начать заново. При отсутствии TURN нет захвата микрофона и нет P2P fallback. Проверки на настоящих устройствах/VPS по-прежнему обязательны.

## Состояния и восстановление

Авторитетное состояние — один API-процесс. SQLite хранит историю и журнал переходов; SDP/ICE находятся только в памяти активного вызова. Масштабирование на несколько API-реплик без общего координатора не поддерживается. После перезапуска API незавершённые записи становятся `interrupted`; восстановить старые DTLS-ключи после перезапуска клиента нельзя.

`preparing → ringing → connecting → active → terminal`. `active` означает готовый SDP, а начало разговора (`answered` / `connected_at`) — подтверждённое обоими владельцами устройств медиасоединение. Это исправляет завышенную длительность при отсутствии звука/ICE. Для совместимости со старыми клиентами без `protocol:2` начало истории остаётся на SDP-answer. Полная новая схема требует обновления обоих клиентов и сервера.

Ожидание ответа — 45 секунд, первичное подключение — 60 секунд, восстановление — до 20 секунд, heartbeat владельца устройства — до 50 секунд, предел разговора — 4 часа. Сервер проверяет сроки каждые 5 секунд и перед запросами: точность завершения фонового таймера ±5 секунд. Старые клиенты сохраняют 60 секунд ожидания ответа. Клиентские таймеры длительности начинаются с WebRTC CONNECTED.

Первый `accept` закрепляет устройство. Остальные получают `CALL_ANSWERED_ELSEWHERE`, не получают дальнейший SDP и убирают входящий вызов. Встречные звонки разрешаются сервером: первый созданный занимает обоих участников, второй получает 409 «занято».

При DISCONNECTED/FAILED клиент показывает восстановление и запрашивает ICE restart. Offer создаёт только исходящий участник; входящий отвечает в том же PeerConnection. Сервер увеличивает `restart_generation`, очищает старый answer и ждёт подтверждений обоих медиаканалов. Идентификатор вызова, история, треки и время начала сохраняются. Повторяется ровно тот же SDP при потере HTTP-ответа. Старое поколение не может подтвердить новый медиаканал. Через 20 секунд без восстановления звонок завершается. SSE ускоряет получение состояния; опрос каждые 2 секунды остаётся страховкой при потере событий. Отмена освобождает медиа и отменяет задачи восстановления; поздние ответы не оживляют звонок.

## API дополнения

Все пути ниже начинаются с `/api`, требуют Bearer авторизацию. Владельцы передают `device` (32 hex), идентификатор звонка — 32 hex. Уведомление не даёт права принять вызов.

| Запрос | Назначение |
|---|---|
| `POST /calls/start {device,chat_id,video,protocol:2,client_id}` | Ключ client_id: 16–64 букв/цифр/дефисов, уникален для пользователя. Повтор возвращает тот же вызов, в том числе завершённый. Другой чат/устройство с тем же ключом — 409. |
| `POST /calls/:id/accept {device,protocol:2}` | Атомарный выбор устройства. Повтор тем же устройством безопасен. |
| `GET /calls/:id?device=…` | Текущий снимок или терминальное состояние; только участники. |
| `POST /calls/:id/media-state {device,connected,restart_generation}` | Подтверждение медиаканала; начало длительности после обоих подтверждений. |
| `POST /calls/:id/ice-restart {device}` | Запрос восстановления. |
| `POST /calls/:id/ice-restart {device,description,restart_generation}` | Только инициатор, новое ICE offer. Повтор с тем же offer безопасен. |
| `POST /calls/:id/answer {device,description,restart_generation}` | Answer восстановления, поколение обязательно. Повтор идентичного ответа безопасен. |
| `POST /calls/:id/end {device}` | Идемпотентное завершение владельцем устройства. |
| `GET /calls/config?call_id=…` | ICE credentials, relay policy обоих участников, доступность TLS и таймауты. |
| `GET/POST /calls/privacy` | `allow_calls`: everyone/contacts/nobody, `relay_only`: boolean; ответ содержит собственный список блокировок. |
| `POST /calls/blocks/:peer {blocked:boolean}` | Блокировка звонков в обе стороны; активный разговор с этим пользователем завершается. До 500 исключений. |

Любая мутация конкретного звонка может передать `expected_version`: несоответствие возвращает 409 `STALE_CALL_VERSION`. Изменения состояния получают возрастающую `version`. Повторы start/offer/accept/answer/end не создают второй звонок или второй переход. Неавторизованный участник получает 404, приватные причины запрета звонка не раскрываются. Частота создания — до 10 попыток в минуту, всего до 100 активных вызовов на API.

События SSE содержат `event_id,call_id,type,sequence,schema_version,sent_at,expires_at,payload.chat_id`. Клиент получает свежий снимок, не применяет старую версию поверх новой. После разрыва SSE используется snapshot, а не воспроизведение SDP из журнала. `call_events` содержит только ID, тип, версию, время; SDP, ICE-адреса, медиа и секреты туда не записываются. Записи старше 30 дней удаляются при запуске API. Heartbeat не создаёт запись в журнале.

## Приватность и криптографические границы

Android: Настройки → Звонки. Windows/Web: Настройки → Звук и камера. Можно разрешить всем, контактам (по серверной книге получателя), никому, заблокировать звонки из профиля и снять блокировку в настройках. Это блокировка звонков, не сообщений. Обязательный режим TURN применяет `iceTransportPolicy:relay` и скрывает локальные ICE-адреса от собеседника; при недоступном TURN прямой маршрут не используется.

Медиа использует WebRTC DTLS-SRTP, TURN пересылает зашифрованные пакеты. В интерфейсе есть код проверки: SHA-256 от домена `volna-call-safety-v1`, ID звонка и отсортированных SHA-256 DTLS fingerprints; отображаются первые 64 бита в четырёх hex-группах. Android и Web используют общий тестовый вектор. Сравнивать по другому доверенному каналу; при различии завершить разговор. Не принимаются отсутствующие, неоднозначные или повреждённые fingerprints.

Это **не** Telegram DH/MTProto, не аудит криптографии и не защита от скомпрометированного устройства. Без сравнения кода доверяем доставке SDP через HTTPS/API. Сервер управляет сигнализацией, видит участников/время/сетевые метаданные. Не публикуйте дампы SDP и полные credentials в диагностике. Права микрофона обязательны, при отказе камеры голосовой звонок доступен. Фоновые ограничения Android и DND остаются под контролем системы.

## TURN и эксплуатация

Обычный TURN UDP/TCP 3478 остаётся совместимым. TCP 3478 не равен TLS 443. Для сетей с запретом UDP добавлен `TURN_TLS_URLS=turns:turn.example.com:443?transport=tcp` (список через запятую). Сервер выдаёт краткоживущие HMAC credentials из TURN_SECRET, а не сам секрет.

Готовая отдельная конфигурация — `compose.turn-tls.yaml`, **на отдельном хосте/IP**: порт 443 основного сервера занят HTTPS/Caddy. На TURN-хосте создайте `/secure/turn.env` с правами 600:

```dotenv
TURN_TLS_HOST=turn.example.com
TURN_EXTERNAL_IP=203.0.113.10
TURN_SECRET=<тот же существующий 64-символьный секрет API>
TURN_TLS_CERT_DIR=/secure/turn-certs
```

В каталоге сертификатов нужны реальные `fullchain.pem`, `privkey.pem` для TURN_TLS_HOST. Разрешите TCP 443 и UDP 49160–49200 в firewall и панели VPS, настройте DNS на выделенный IP. Затем:

```sh
docker compose --env-file /secure/turn.env -f compose.turn-tls.yaml up -d
```

После продления сертификата перезапустите turn-tls. На основном сервере добавьте TURN_TLS_URLS в существующий `.env` и пересоздайте API через штатный `scripts/update.sh`. Не заменяйте TURN_SECRET и не передавайте его в публичные логи. Проверка сертификата: `openssl s_client -connect turn.example.com:443 -servername turn.example.com -verify_return_error`. TLS handshake проверяет сертификат, но не TURN allocation: дополнительно проверьте звонок с relay-only и заблокированным UDP на клиентской сети.

При диагностике: версии обоих клиентов/API, время и ID звонка, тип сети, код терминального состояния, наличие TURN/TLS. Для локальной сверки без содержимого разговора:

```sql
SELECT id,status,created,answered,ended,version FROM call_history ORDER BY created DESC LIMIT 20;
SELECT call_id,type,version,created FROM call_events ORDER BY created DESC LIMIT 50;
```

## Приёмка и ограничения проверки

Автотесты проверяют ключ создания, повторы, запрет чужого устройства, версии, начало длительности, терминальные состояния, TTL, ICE поколения, восстановление при потерянном HTTP-ответе, конкурентные callbacks, блокировки, relay config и код проверки ключей. Старые lifecycle/history тесты сохранены. Android собирается с unit/UI suite, Web и desktop renderer — production bundle.

`node tests/call-recovery-ui.mjs` запускает настоящие RTCPeerConnection и проверяет новые ICE credentials, пакеты аудио и одинаковый код после restart, если среда выдаёт ICE-кандидаты. В текущей облачной среде кандидатов нет: тест **SKIP**, реальный сетевой результат не подтверждён.

Перед признанием сетевых SLO выполните на физических Android/Windows/Web:

1. Аудио/видео в одной и разных сетях, мобильная сеть/CGNAT, relay-only, TURN TLS 443 при заблокированном UDP.
2. Приём одновременно на двух устройствах; на проигравшем убрать входящий вызов. Повторный push после отбоя не открывает старый звонок.
3. Переключение Wi-Fi ↔ LTE во время аудио и видео: тот же вызов, без повторного разрешения микрофона, длительность не обнуляется. Отключение связи >20 секунд завершает восстановление.
4. Отмена при согласовании SDP; камера запрещена/микрофон разрешён; отзыв микрофона; Bluetooth отключён; внешний телефонный вызов.
5. Заблокированный экран/фон, Android энергосбережение, приоритетная вибрация и DND. Сравнение кода на обеих платформах.
6. Перезапуск API, обрыв SSE, история пропущенных и выход из аккаунта. Ни один сценарий не должен оставлять микрофон/foreground service после окончания.

Измерения p95 установки, доли успешных звонков и батареи/нагрузки в целевых сетях ещё не выполнены. Выделенный TURN TLS здесь не развёрнут: нужны хост/IP и сертификат владельца. Завершение SFU и полностью Telegram-эквивалентного протокола не заявляется.
