# Волна 0.11.36: исправление запуска распознавания и backup

Ранее сервис загружал модель Whisper до открытия HTTP-порта. Если загрузка занимала больше пяти минут, Docker помечал контейнер `unhealthy`, а сервер Волны не запускался. Дополнительно backup запускал `compose up`, который мог пересоздать сервер из нового образа до завершения обновления.

Исправление переносит загрузку модели в отдельный поток. HTTP-сервис начинает работать сразу; полный локальный кеш используется без запросов к Hugging Face, неполный кеш докачивается. Ошибки загрузки сохраняются в статусе, повтор выполняется через 60 секунд. До готовности модели запросы распознавания получают 503. Backup восстанавливает именно ранее работавшие контейнеры; заранее остановленный сервер остаётся остановленным. Нормальное обновление создаёт новые контейнеры на своём этапе.

## Установка

Загрузите `volna-transcription-startup-fix.zip` в домашний каталог VPS рядом с действующим `volna-messenger`. Архив рассчитан на исходники 0.11.36 и содержит только изменённые файлы, проверки и инструкции:

```sh
cd ~
unzip -o volna-transcription-startup-fix.zip -d .
cd volna-messenger
VOLNA_BUILD_NETWORK=host sh scripts/update.sh
```

Режим сети хоста сохранён из предыдущего исправления DNS и применяется к сборочным шагам. `.env`, база, вложения, ключ Android, кеши и уже опубликованные APK/EXE остаются в действующем проекте. Обновление собирает сервер, Web и распознавание; версия клиентов остаётся **0.11.36**. Кеш моделей удалять не нужно.

## Проверка после запуска

```sh
docker compose ps -a
docker compose logs --tail=80 transcription
docker compose exec -T transcription python -c 'import json,urllib.request; print(json.load(urllib.request.urlopen("http://127.0.0.1:8000/health",timeout=5)))'
```

`ready: True`, `state: ready` означают готовность к распознаванию. `state: loading` означает загрузку. `state: failed` означает ошибку; поле `error` содержит тип, errno и HTTP-статус, если они доступны. Контейнер при этом может быть `healthy`: это подтверждает работу HTTP-сервиса, а готовность модели проверяется отдельно. В журнале успешная загрузка отмечена `[whisper] model_ready`.

По исходному сообщению точная причина сбоя модели на VPS не установлена. Сеть, свободное место, права на кеш и память требуют проверки по реальному журналу. Если состояние остаётся `failed` либо контейнер перезапускается, пришлите вывод:

```sh
docker compose logs --tail=120 transcription
docker inspect "$(docker compose ps -aq transcription)" --format 'status={{.State.Status}} exit={{.State.ExitCode}} oom={{.State.OOMKilled}} error={{.State.Error}} health={{json .State.Health}}'
```

Исправление не делает недоступный источник модели доступным: оно устраняет блокировку запуска переписки и показывает ошибку отдельно. Распознавание начинает работать после успешной загрузки модели.

## Проверки

81 Node-проверка и 8 Python-проверок. Python запускает настоящий FastAPI/Uvicorn HTTP-сервис с подставленным загрузчиком/моделью: медленная загрузка не задерживает открытие порта; до готовности возвращается 503; ошибки доступны в статусе; готовая модель обрабатывает запрос, временный файл удаляется. Проверены повтор загрузки, остановка, полный/неполный кеш. Эти Python-проверки также выполняются при сборке Docker-образа.

Проверки backup используют настоящий shell-скрипт с подставленным Docker: успешная и неудачная копия восстанавливают прежний сервер, остановленный сервер не запускается. Docker, реальные веса Whisper и ваш VPS здесь не запускались.
