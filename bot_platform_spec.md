# ТЕХНИЧЕСКОЕ ЗАДАНИЕ
## Серверная платформа ботов (Bot Platform) для собственного мессенджера

**Версия:** 1.0 (проект для согласования)  
**Дата:** 16 октября 2026 г.  
**Заказчик:** владелец мессенджера  
**Объект разработки:** backend-подсистема Bot Platform и необходимые интерфейсы интеграции  
**Статус:** техническая спецификация для оценки, проектирования, реализации и приёмки  

> Важно. Это проект ТЗ на базе согласованных продуктовых решений, а не описание внутреннего исходного кода Telegram. Числовые лимиты, SLA и технологические решения в разделах, отмеченных как «проектные», подлежат утверждению после оценки текущего backend мессенджера.

## 1. Цель и ожидаемый результат

Разработать многопользовательскую (multi-tenant) платформу ботов, позволяющую третьим лицам создавать специальные аккаунты ботов в мессенджере, подключать их к внешнему серверу либо развертывать в управляемой среде платформы, получать разрешённые события и выполнять операции через версионированный HTTPS Bot API.

По результатам внедрения разработчик должен иметь возможность: создать бота, получить токен, выбрать режим исполнения, настроить получение событий, отправить сообщение в разрешённый чат, обработать команду/кнопку, использовать медиа и увидеть диагностическую информацию. Пользователи мессенджера должны видеть бота как отдельного участника личного или группового чата, иметь возможность управлять доступом и блокировкой.

### 1.1. Зафиксированные решения

| Код | Решение | Статус |
|---|---|---|
| D-01 | Внешнее исполнение (External Bot) + размещение кода платформой (Hosted Bot) | Обязательно в v1 |
| D-02 | Webhook + Long Polling | Обязательно в v1 |
| D-03 | Полный доступ к группе возможен при явном разрешении администратора | Обязательно в v1 |
| D-04 | Гибридная модель: server-readable и E2EE чаты | Обязательно учитывать архитектурно |
| D-05 | В v1 Bot API читает содержимое только server-readable чатов; E2EE-боты не поддерживаются без отдельной криптографической реализации | Безопасное ограничение v1 |
| D-06 | Текст, inline-кнопки, команды, медиа | Обязательно в v1 |

### 1.2. Не входит в v1

Платежи и возвраты, Mini Apps/WebView SDK, публикация в публичном каталоге с модерацией, монетизация ботов, голосовые звонки, произвольный доступ к истории переписки, исполнение произвольных пользовательских Docker-контейнеров без ограничений, совместимость 1:1 со всеми методами Telegram Bot API, использование ботов в E2EE-переписке как полноценных криптографических участников. Эти функции допускается проектировать как последующие расширения.

## 2. Границы системы и определения

**Бот:** специальный аккаунт в системе identity мессенджера с `account_type=bot`. **Владелец:** авторизованный пользователь/организация, управляющий ботом. **External Bot:** приложение, исполняемое у стороннего разработчика, с получением событий по webhook/polling. **Hosted Bot:** загружаемый разработчиком код, исполняемый в управляемой изолированной среде. **Bot API:** публичный HTTPS API для выполнения операций от имени бота. **Update:** разрешённое событие, предназначенное определённому боту. **Chat Grant:** разрешение боту участвовать в чате и выполнять определённые действия. **Server-readable:** режим, в котором сервер вправе обрабатывать текст/метаданные сообщения в рамках правил приложения. **E2EE:** режим, в котором сервер доставки не располагает открытым содержимым переписки.

### 2.1. Обязательные интеграции с существующим backend

- Identity/Auth: единая таблица аккаунтов и идентификаторы пользователей; бот имеет обычную маршрутизируемую identity с типом `bot`.
- Chat/Membership: проверка участников и роли, добавление/удаление бота, права группы, блокировка в личном чате.
- Messaging: единая транзакционная запись сообщений, идентификаторов, статусов, idempotency и доставка клиентам.
- Realtime/Push: WebSocket или иные существующие клиентские каналы синхронизации; push-уведомления по действующей политике.
- Files/Media: объектное хранилище, права на скачивание, метаданные файлов и обработка безопасных типов.
- Encryption: маркировка режима чата, запрет plaintext-доступа к E2EE и согласованная политика membership.
- Trust & Safety: блокировки, rate limiting, отчёты о спаме, аудит операций администратора.

Все backend-процессы, создающие сообщения от имени ботов, обязаны использовать единый Messaging Service. Непосредственная запись бот-сервисом в таблицу `messages` вне согласованного сервисного контракта запрещена.

## 3. Логическая архитектура

```text
                         MESSENGER CLIENTS
                       mobile / desktop / web
                                |
                         API / WebSocket
                                |
                       MESSENGER BACKEND
              +-----------------+-----------------+
              | Identity / Chat / Messaging / Files |
              +-----------------+-----------------+
                                |
                     TRANSACTIONAL OUTBOX
                                |
                          EVENT BROKER
                                |
                 BOT ROUTER / POLICY FILTER
                                |
                     DURABLE BOT UPDATE LOG
                         /             \
            External Delivery       Hosted Dispatcher
             /          \                |
          Webhook       Polling      Sandboxed Runtimes
             \          /                |
              +--------+-----------------+
                       BOT API GATEWAY
                                |
                       MESSAGING SERVICE
```

### 3.1. Control Plane

Содержит Developer API/Portal, Bot Registry, управление владельцами, credentials, разрешениями, режимом исполнения, webhook, конфигурациями runtime, деплоями, секретами и аудитом. Авторизуется обычной пользовательской/организационной сессией; API-токен бота **не** предоставляет доступ к управлению владельцем или созданию других ботов.

### 3.2. Data Plane

Содержит Bot API Gateway, Policy/Authorization Engine, Event Router, update log, delivery workers, polling handlers, Bot Media API и адаптер Messaging Service. Масштабируется независимо от Control Plane.

### 3.3. Hosted Execution Plane

Содержит Build Service, Artifact Registry, Deployment Controller, изолированные исполнения (microVM либо эквивалентная сильная sandbox-изоляция), Secrets Broker, ограниченный egress, маршрутизацию событий из общего update log, stdout/stderr-логи и счётчики ресурсов.

### 3.4. Развёртывание

Допускается модульный монолит на старте (Control Plane + Data Plane) с отдельными очередями и workers. Hosted Execution Plane обязательно изолировать от основных БД, секретов и системных сетей. Не требуется выделять микросервис на каждую логическую сущность.

## 4. Функциональные требования: реестр ботов

| ID | Требование | Приёмка |
|---|---|---|
| REG-01 | Авторизованный владелец создаёт бота с уникальным username, названием и описанием | Дубликат username -> 409 |
| REG-02 | Бот создаётся как account_type=bot и связан с owner_id | Сообщения отражаются как бот в общем messaging |
| REG-03 | Статусы `active`, `suspended`, `deleted` | suspended запрещает API и доставку |
| REG-04 | Управление внешним/размещённым режимом | Одновременно активен только один execution mode |
| REG-05 | Просмотр/изменение метаданных, аватара, команды, настроек | Изменения логируются |
| REG-06 | Ротация/отзыв токенов без утечки старых значений | Отозванный токен -> 401 |
| REG-07 | Роли owner, maintainer, viewer в Developer Portal | Запрещённые действия -> 403 |
| REG-08 | Список ботов пользователя и фильтрация по статусу | Видны только доступные субъекту боты |
| REG-09 | Удаление/выключение бота с политикой освобождения username | Понятный lifecycle и аудит |

Рекомендуемые поля бота: `id UUID`, `account_id UUID UNIQUE`, `owner_id UUID`, `username CITEXT UNIQUE`, `display_name VARCHAR(128)`, `description TEXT`, `execution_mode external|hosted`, `status`, `default_visibility restricted`, `created_at`, `updated_at`. Username проверяется нормализацией, защитой от конфузаблов и резервированными именами; display_name не считается уникальным.

## 5. Аутентификация и авторизация

### 5.1. Аутентификация

- Public Bot API: `Authorization: Bearer <bot_token>`. Токены имеют случайность не менее 256 бит, передаются только через TLS, показываются при выпуске однократно и хранятся в БД как защищённый HMAC/хеш с уникальным публичным префиксом для lookup.
- Developer API: действующая пользовательская/организационная сессия, роль владельца, CSRF-защита browser-flow.
- Hosted Bot: краткоживущий workload-токен, привязанный к deployment/bot, доступный только экземпляру runtime, с возможностью автоматической ротации. Постоянный bot_token в контейнер не внедряется.
- Webhook: HMAC-SHA256 от timestamp + raw body с отдельным секретом; проверку подписи выполняет получатель. Устанавливаются окно timestamp и защита от повторного воспроизведения.

### 5.2. Проверки на каждую операцию

API Gateway валидирует токен, статус бота, rate limit, scope метода, `chat_id`, membership, режим шифрования, блокировку со стороны пользователя, роль бота в группе и владение ресурсом. Прямое знание `chat_id`/`message_id` не означает права доступа. Информация о недоступных ресурсах не должна облегчать перечисление чужих чатов.

### 5.3. Набор разрешений (scopes)

`messages:send`, `messages:edit_own`, `messages:delete_own`, `messages:read_events`, `media:upload`, `chats:read_basic`, `callbacks:answer`, `commands:manage`, `groups:read_all`, `groups:moderate` (последний зарезервирован, если модерация не входит в v1). Scope токена и chat grant должны разрешать действие **одновременно**.

## 6. Модель чатов, групп и приватности

### 6.1. Личные чаты

Первый диалог запускается действием пользователя (`start`, открытие и подтверждение диалога или разрешённый deep link). Бот не вправе самостоятельно писать произвольным пользователям. Пользователь может блокировать/разблокировать бота; блокировка запрещает `messages.create` и прекращает новые доступные события. Удаление переписки не равно блокировке — семантика определяется Messaging Service.

### 6.2. Группы

Бот добавляется в группу пользователем с необходимыми полномочиями. При добавлении активен `restricted`-режим: команды, прямые упоминания, ответы на сообщения бота и сервисные события. `full_read`-режим разрешается только администратором группы отдельным действием, фиксируется в `bot_chat_grants`, доводится до участников интерфейсом мессенджера и не даёт больше прав, чем реально выдано. Права на отправку, удаление, закрепление, чтение чужих сообщений и администрирование независимы. Любое изменение прав отражается в событии `bot.permissions_changed`.

### 6.3. Изоляция bot-to-bot

По умолчанию сообщения, отправленные ботом, не транслируются другим ботам как пользовательские события, чтобы избежать циклов. Обработчик конкретного бота никогда не получает callback, относящийся к чужому боту. Исключения требуют отдельного feature flag и архитектурного согласования.

### 6.4. Гибридное шифрование — обязательные правила

В каждой записи чата существует неизменяемый либо управляемый отдельной процедурой `encryption_mode = server_readable|e2ee` с явной миграционной политикой; режим не может незаметно переключаться на уровне отдельного сообщения. В `server_readable` Bot Event Router может передавать plaintext и разрешённые метаданные, при соблюдении ACL. В `e2ee` серверу не передаются ключи пользователей и он не предоставляет Bot API открытое содержимое сообщений и вложений. Добавление обычного внешнего/hosted бота в E2EE-чат в v1 запрещено кодом `E2EE_BOT_UNSUPPORTED`; допустимо предложить отдельный server-readable чат с явным согласием, но нельзя прозрачно переводить существующую переписку в менее приватный режим.

Будущее расширение: E2EE-бот должен выступать отдельным криптографическим endpoint/участником с управлением ключами, учётом эпох и явным информированием всех участников. В качестве стандарта для групповой криптографии можно оценивать MLS (RFC 9420), но внедрение протокола и модель устройств не входят в данное v1-ТЗ.

## 7. Жизненный цикл сообщения

1. Клиент авторизованного пользователя отправляет сообщение в Messaging API.
2. Messaging Service проверяет ACL и шифрование, транзакционно сохраняет сообщение и outbox-запись.
3. После COMMIT outbox publisher публикует доменное событие; сбой publisher не теряет outbox-запись.
4. Event Router определяет ботов-получателей и применяет разрешения **на момент формирования bot update**; события по E2EE plaintext не создаются.
5. Для каждого подходящего бота формируется отдельная запись `bot_updates` с уникальными `event_id` и монотонным `update_id` в пределах бота.
6. Delivery Engine отправляет update выбранным транспортом либо Hosted Dispatcher передаёт его в sandbox.
7. Бот формирует ответ через Bot API. Messaging Service сохраняет его обычным способом.
8. Realtime Service доставляет ответ клиентам; API-успех означает «принято/сохранено», а не «прочитано».

Не допускается синхронное ожидание webhook при отправке пользовательского сообщения. Необходимо документировать различие между статусами `accepted`, `delivered_to_device` и `read`.

## 8. Модель событий и гарантии

### 8.1. Общая обёртка update

```json
{
  "update_id": 1042,
  "event_id": "evt_01JZABC000001",
  "event_type": "message.created",
  "api_version": "1",
  "bot_id": "bot_01JZBOT001",
  "occurred_at": "2026-10-16T10:00:00Z",
  "chat_id": "chat_01JZ001",
  "chat_sequence": 409,
  "data": {
    "message": {
      "id": "msg_01JZ001",
      "chat_id": "chat_01JZ001",
      "sender": {"id": "usr_01JZ001", "display_name": "Alex"},
      "type": "text",
      "text": "Привет",
      "created_at": "2026-10-16T10:00:00Z"
    }
  }
}
```

`event_id` не меняется между повторными доставками; `update_id` — BIGINT, монотонный **для одного бота** и используется как курсор Polling; `chat_sequence` — последовательность в чате для анализа порядка. Глобальный строгий порядок webhook-доставок не гарантируется; параллельные delivery workers могут доставлять события вне порядка, особенно после retry. Внешние боты обязаны быть идемпотентными по `event_id`.

### 8.2. События v1

| Событие | Важные поля | Условие маршрутизации |
|---|---|---|
| `message.created` | message, chat, sender, attachments | Доступ к сообщению по privacy/ACL |
| `message.edited` | message_id, revision, new_content | Бот имел и сохраняет право видеть сообщение |
| `message.deleted` | message_id, deleted_at | Бот имел право видеть факт удаления |
| `callback.created` | callback_id, actor, message_id, data, expires_at | Кнопка создана этим ботом |
| `chat.member_added` | chat_id, actor_id, member_id | Бот состоит в чате и событие разрешено |
| `chat.member_removed` | chat_id, member_id | Аналогично |
| `bot.added_to_chat` | chat_id, initial_permissions | Бот добавлен |
| `bot.removed_from_chat` | chat_id, reason | Бот удалён |
| `bot.permissions_changed` | chat_id, effective_permissions | Изменены права |

Содержимое данных должно минимизировать PII: не отправлять телефон, email, IP, сессии и профили пользователей, если они специально не раскрыты соответствующим отдельным API и разрешением.

### 8.3. Гарантии

- `at-least-once` для событий в пределах срока хранения и действующей подписки; дубликаты допустимы.
- Durable update log переживает перезапуск API/worker.
- Рекомендуемое хранение ожидающих событий: 72 часа после `occurred_at`; после истечения `expired` с агрегированной метрикой (проектное значение).
- Dead Letter Queue: неудачные доставки с причиной, финальным HTTP status и метаданными; не хранить без срока живой plaintext.
- Строгий `exactly-once` end-to-end **не обещается**; действия бота защищаются idempotency keys.
- В случае отзыва права доступа ранее накопленные, но не доставленные события должны быть отфильтрованы/редактированы при выдаче, если их содержимое более не разрешено.

## 9. Транспорт Webhook

### 9.1. Конфигурация

`PUT /bot/v1/delivery/webhook` с телом `{ "url": "https://bot.example.com/events", "event_types": ["message.created", "callback.created"] }` включает webhook и атомарно выключает Polling. Сервер проверяет URL до сохранения; не разрешает IP внутренней сети, localhost, metadata IP, незащищённый HTTP или перенаправление в недоверенную сеть.

### 9.2. Доставка

HTTP POST `application/json`, заголовки `X-Bot-Event-Id`, `X-Bot-Timestamp`, `X-Bot-Signature`. Подпись: `hex(HMAC-SHA256(webhook_secret, UTF8(timestamp + "." + raw_http_body)))`; заголовок `X-Bot-Signature: sha256=<lowercase-hex>`, допустимый сдвиг timestamp — не более 300 секунд (проектно). Получатель обязан сравнивать подписи константным по времени способом и проверять replay по event_id. Получение HTTP 2xx в пределах 5 секунд подтверждает доставку; любой другой исход означает retry. Рекомендуемая политика: экспоненциальные задержки с jitter и максимальной длительностью до TTL update, ограничение одновременных доставок на одного бота, circuit breaker при продолжительных ошибках. 3xx не следует автоматически исполнять; необходимо повторно валидировать IP для каждого нового DNS resolve и на момент соединения. 

### 9.3. Безопасность

Outgoing webhook работает в выделенной egress-сети без доступа к control-plane, БД и приватным сервисам. Внешний разработчик получает секрет подписи отдельно; webhook не получает постоянный bot token платформы. Сертификаты TLS проверяются; запрет на обход проверки сертификата. Запросы логируются только с редактированием секретов/PII.

## 10. Транспорт Long Polling

`GET /bot/v1/updates?offset=1043&limit=100&timeout=30` доступен только в режиме polling. Параметры: `offset` (следующий update_id, подтверждает все меньшие), `limit` 1..100, `timeout` 0..30 секунд. Одновременно разрешён один активный polling-запрос на бота; второй — `409 POLLING_ALREADY_ACTIVE` (предлагаемая политика). Данные возвращаются в порядке `update_id` по возрастанию. Только вызов с более высоким offset подтверждает ранее полученные updates; таймаут без данных ничего не подтверждает. Нельзя включить webhook и polling одновременно.

Изменение режима должно быть атомарным, с сохранением непрочитанных updates и зафиксированного курсора; при переключении server-issued generation/version предотвращает одновременную выдачу через два транспорта. Старые неподтверждённые события остаются доступными в пределах TTL (если право их выдачи не отозвано).

## 11. Hosted Bot Runtime (обязательная часть v1)

### 11.1. Поддерживаемая модель

В v1 разработчик может загрузить package `.zip` с `manifest.json` и кодом на одном поддерживаемом серверном runtime (предлагается Node.js LTS; конкретная версия фиксируется в эксплуатационной документации). Build Service формирует immutable artifact (OCI image либо эквивалент), проверяет пакет и создаёт версионированный deployment. Использование произвольного непроверенного привилегированного Docker image запрещено. Пользовательский код **никогда** не исполняется в процессах core backend.

### 11.2. Пример manifest

```json
{
  "schema_version": 1,
  "runtime": "nodejs-lts",
  "entrypoint": "dist/index.js",
  "handler": "onEvent",
  "required_scopes": ["messages:send", "messages:read_events"],
  "memory_mb": 256,
  "timeout_seconds": 10
}
```

### 11.3. Изоляция и ограничения

Обязательно: отдельная sandbox-граница (предпочтительно microVM или документированная изоляция эквивалентной силы); непривилегированный пользователь; read-only root FS; эфемерная writable-папка с quota; без доступа к host socket, kernel capabilities, namespace других ботов, metadata service и внутренним БД; seccomp/изоляция syscalls; ограничения CPU, RAM, concurrency, диска, сетевого трафика, числа логов и времени исполнения. Egress — deny by default, разрешаемый через политики доменов/портов с проверкой IP на сетевом уровне. Sandbox должна считаться границей для недоверенного кода; контейнер **сам по себе** не считается достаточным доказательством безопасности.

### 11.4. Доставка событий hosted-боту

Hosted Dispatcher читает тот же durable update log, что и внешние транспорты; отдаёт событие в активную sandbox-инстанцию по внутреннему доверенному протоколу. В v1 подтверждение происходит после успешного завершения асинхронного обработчика `onEvent(update)`; ошибка/таймаут не подтверждают событие. SDK обязан обеспечить дедупликацию внешних эффектов по `event_id`. При timeout/crash событие повторяется с тем же `event_id` до TTL. Hosted-бот пользуется тем же Bot API, но через краткоживущую workload identity. Любой callback/outbound API вызов обязан проходить общие ACL и лимиты.

### 11.5. Управление жизненным циклом

Статусы deployment: `uploaded`, `building`, `failed`, `ready`, `deploying`, `active`, `rollback`, `disabled`. Поддержать вывод логов с маскированием секретов; просмотр метрик, отмену, rollback на предыдущую успешную версию, stop/start; на один бот в v1 активен один deployment. Смена `external` -> `hosted` атомарно меняет транспорт и workload identity, сохраняя update log. Для hosted допускается `scale-to-zero`, если обеспечивается пробуждение без потери событий.

### 11.6. Проектные начальные квоты Hosted

Пакет до 50 MiB, RAM 256 MiB, CPU до 0,5 vCPU на вызов, timeout обработчика 10 секунд, max 2 параллельных вызова на бота, log retention 7 дней, egress deny by default. Числа согласуются после load/security test и не являются обязательными характеристиками инфраструктуры заказчика.

## 12. Публичный Bot API v1

Базовый URL `https://api.<messenger-domain>/bot/v1`. JSON UTF-8; HTTPS; Bearer token для внешних ботов. Названия и тела являются **контрактом собственной платформы**, а не совместимым клоном Telegram. ID — непрозрачные строки. Для POST, создающих ресурс, используется `Idempotency-Key` длиной 16..128 ASCII символов; сохранение результата минимум 24 часа. Повтор с тем же ключом/телом возвращает прежний результат, с другим телом -> 409.

| HTTP | Путь | Назначение | Scope |
|---|---|---|---|
| GET | `/me` | Сведения о боте | token valid |
| POST | `/messages` | Текст/медиа/кнопки | messages:send |
| PATCH | `/messages/{message_id}` | Изменить своё сообщение | messages:edit_own |
| DELETE | `/messages/{message_id}` | Удалить своё сообщение | messages:delete_own |
| GET | `/chats/{chat_id}` | Базовые разрешённые сведения о чате | chats:read_basic |
| PUT | `/commands` | Установить команды | commands:manage |
| GET | `/commands` | Список команд | token valid |
| PUT | `/delivery/webhook` | Включить/изменить webhook | token valid |
| DELETE | `/delivery/webhook` | Отключить webhook | token valid |
| GET | `/updates` | Long Polling | messages:read_events |
| POST | `/callbacks/{callback_id}/answer` | Ответить на callback | callbacks:answer |
| POST | `/files/uploads` | Создать загрузку | media:upload |
| POST | `/files/{file_id}/complete` | Подтвердить загрузку | media:upload |
| GET | `/files/{file_id}` | Получить доступные метаданные файла | media:upload либо право чтения |

### 12.1. POST /messages: пример

```http
POST /bot/v1/messages
Authorization: Bearer <TOKEN>
Idempotency-Key: 3bbdf588-a7b2-4767-a746-76c94f0d9cb4
Content-Type: application/json
```

```json
{
  "chat_id": "chat_01JZ001",
  "type": "text",
  "text": "Выберите действие",
  "reply_to_message_id": null,
  "reply_markup": {
    "inline_keyboard": [[
      {"text": "Каталог", "callback_data": "catalog"},
      {"text": "Помощь", "callback_data": "help"}
    ]]
  }
}
```

Ответ `201`:

```json
{
  "id": "msg_01JZ002",
  "chat_id": "chat_01JZ001",
  "sender_id": "bot_01JZBOT001",
  "status": "accepted",
  "created_at": "2026-10-16T10:00:01Z"
}
```

Правила валидации: UTF-8; `text` до 4096 Unicode code points (проектный предел); кнопка `text` до 64 символов; `callback_data` до 128 байт UTF-8; до 8 строк по 8 кнопок (проектно); запрещены невалидные/неизвестные типы; `reply_to_message_id` должен существовать в том же чате и быть доступным. `client_message_id` не доверяется как серверный идентификатор. HTML/Markdown форматирование в v1 необязательно и не должно позволять внедрение активного HTML.

### 12.2. Media message

```json
{
  "chat_id": "chat_01JZ001",
  "type": "image",
  "file_id": "file_01JZ123",
  "caption": "Фото товара"
}
```

### 12.3. PATCH /messages/{id}

Разрешено изменение только собственных сообщений бота с проверкой ревизии `If-Match`/`revision` во избежание гонок. Вернуть `200` с обновлённой ревизией; отсутствие прав -> 403; чужая либо недоступная запись -> 404/403 по privacy policy. Поддержка редактирования caption и клавиатуры для собственных сообщений в v1; смена автора запрещена.

### 12.4. DELETE /messages/{id}

Удаляет собственное сообщение для всех участников, если политика чата разрешает; операция идемпотентна, статус 204. Удаление чужих сообщений требует отдельного модераторского API, вне обязательного v1.

### 12.5. Callback-обработка

Callback привязан к конкретной кнопке и авторизованному пользователю. Клиент отправляет **внутренний** authenticated interaction request с `message_id`, `button_id`, сервер находит сохранённый callback_data и создаёт `callback.created`; подменять actor_id, bot_id, callback_data с клиента запрещено. `POST /callbacks/{callback_id}/answer` возвращает краткий UI-ответ либо alert (проектный TTL callback: 120 секунд). Дубли одного физического нажатия подавляются через client interaction id.

### 12.6. Команды

`PUT /commands` принимает массив `{command, description}` (до 100 команд; имя `^[a-z0-9_]{1,32}$` — проектно). Команды `/start`, `/help` являются обычными отправляемыми пользователем сообщениями; возможно отдельное parsed `command` поле внутри message event. Клиент показывает меню из полученного списка.

### 12.7. Стандартизованный ответ с ошибкой

```json
{
  "error": {
    "code": "CHAT_ACCESS_DENIED",
    "message": "Bot cannot write to the specified chat",
    "request_id": "req_01JZABC",

  }
}
```

## 14. Файлы и медиа

Двухшаговая загрузка: `POST /files/uploads` возвращает `upload_id`, `file_id`, короткоживущий pre-signed PUT URL и ограничения; клиент загружает файл в Object Storage, затем `POST /files/{file_id}/complete` запускает проверку реального MIME/size, антивирусную проверку и декодирование превью. Статусы: `pending`, `uploaded`, `scanning`, `ready`, `rejected`, `expired`. Сообщение с `file_id` создаётся только когда файл `ready`. Проверка принадлежности/доступа к файлу выполняется при отправке и скачивании.

Проектные пределы v1: изображения JPEG/PNG/WebP до 20 MiB, документы до 50 MiB; видео/аудио допускаются только при наличии соответствующего media pipeline. Скачать файл можно по краткоживущему подписанному URL, выдаваемому после ACL check. Filename, URL и MIME не должны использоваться как доверенные пути/типы. Для E2EE вложений сервер рассматривает ciphertext как непрозрачные байты; антивирусная проверка plaintext на сервере невозможна.

## 15. PostgreSQL: логическая схема БД

В качестве базового транзакционного хранилища рекомендуется PostgreSQL, с учётом существующих таблиц `accounts`, `chats`, `chat_members`, `messages` и `files`. Ниже приведены **поля и ограничения**, которые разработчик должен учесть; конкретные внешние ключи и типы ID адаптируются к текущему backend.

| Таблица | Основные поля | Ключи / индексы |
|---|---|---|
| `bots` | id, account_id, owner_id, username, display_name, status, execution_mode, timestamps | PK id, UQ account_id, UQ normalized_username, IDX owner_id |
| `bot_members` | bot_id, user_id, role, created_at | PK(bot_id,user_id) |
| `bot_tokens` | id, bot_id, token_prefix, secret_digest, scopes_json, expires_at, revoked_at | UQ prefix, IDX bot_id |
| `bot_webhooks` | bot_id, url, secret_ref, subscribed_types, enabled, generation, updated_at | PK bot_id |
| `bot_delivery_state` | bot_id, mode, generation, polling_confirmed_update_id, next_update_id | PK bot_id |
| `bot_updates` | bot_id, update_id, event_id, chat_id, type, payload_json, occurred_at, expires_at, acked_at, delivery_state | PK(bot_id,update_id), UQ(bot_id,event_id), IDX(bot_id,delivery_state,expires_at) |
| `bot_delivery_attempts` | id, bot_id, update_id, attempt, status_code, error_code, elapsed_ms, next_retry_at | IDX(bot_id,update_id), IDX next_retry_at |

| `bot_callback_requests` | id, action_id, actor_id, state, expires_at, answered_at | UQ interaction/client_nonce where applicable |
| `bot_idempotency` | bot_id, method, resource, key, request_hash, response_blob, status_code, expires_at | UQ(bot_id,method,resource,key) |

Для больших объёмов предусмотреть партиционирование по времени/боту и периодическую очистку согласно retention. В таблицах не хранить plaintext webhook secrets. В `bot_delivery_attempts` не дублировать содержимое сообщений. Любые каскадные удаления должны быть согласованы с retention и аудитом.

## 16. Очереди, атомарность и обработка сбоев

- Запись сообщения + `event_outbox` фиксируются одной транзакцией. Publisher идемпотентно публикует outbox в broker; повтор не создаёт второй логический `event_id`.
- Event Router выполняет fan-out только авторизованным ботам и делает `INSERT ON CONFLICT DO NOTHING` по `(bot_id,event_id)`.
- Для webhook доставок ведётся durable state и retry schedule; 2xx приводит к ack, 408/429/5xx и timeout — к retry; 4xx без retry всё равно отражаются в диагностике и завершаются по настраиваемой политике (на v1 рекомендуется retry до TTL, кроме ошибок конфигурации, требующих ручного исправления).
- Для polling запрос с `offset` подтверждает updates ниже offset только при последовательной проверке существования/видимости; высокие произвольные offsets не должны позволять бесконтрольно потерять данные без явного подтверждения протокола.
- Для hosted обработчик возвращает ack или failure. Crash/runtime timeout -> retry с тем же event_id; при длительном падении deployment — автоматически приостановить выдачу и показать degraded.
- Очереди должны выдерживать медленного tenant без блокировки остальных; нужны per-bot concurrency/quotas, global backpressure и DLQ.

## 17. Ограничения, безопасность, комплаенс

### 17.1. API и токены

TLS 1.2+ (предпочтительно TLS 1.3), запрет логирования `Authorization`, секреты в vault, индексация токенов через prefix/digest, ротация, аудит выдачи и отзыва, WAF/bot protection, CORS по политике, защита CSRF на портале, idempotency и повторный ACL check, запрет горизонтального повышения привилегий (IDOR).

### 17.2. SSRF и webhook

Проверять URL и конечные IP, DNS rebinding, IPv4/IPv6, редиректы, link-local, приватные адреса, метаданные облака; выделенный egress proxy. На уровне ОС/сети запретить доступ worker к private networks. Повторные DNS-resolve при соединении не должны обходить фильтр. HTTP response body ограничен в размере и не логируется без необходимости.

### 17.3. Модерация и PII

Механизм блокировки бота, аварийного отключения токена и hosted deployment. Отдельные лимиты: запросы/token, бот/чат, сообщения/пользователь, создание ботов/owner, медиа/сутки, события/бот, hosted CPU/RAM. Privacy-by-default: внешним ботам не передаются IP, номер телефона, email, токены пользователей, список участников без разрешения. Удаление/экспорт персональных данных и сроки хранения — согласно юридической политике продукта (включая применимые нормы GDPR).

### 17.4. Наблюдаемость и секреты Hosted

Данные одного tenant не доступны другому через fs, env, сетевые метаданные, логи и процессы. Секреты не включаются в билд-артефакты и не должны возвращаться в UI после первичной записи; runtime получает их через secrets broker. Сканирование зависимостей и исходных пакетов выполняется на этапе build; sandbox обновляется по политике security patches.

## 18. Нефункциональные требования и проектный baseline

Ниже — **начальные значения для оценки**, требующие утверждения по результатам обследования инфраструктуры:

| Метрика | Предварительная цель | Как измерять |
|---|---|---|
| Регистрация ботов | от 100 000 всего | Структуры/индексы и тест миграции |
| Одновременно активные боты | от 10 000 | 5-мин. активность |
| Bot API, без файлов | 1 000 RPS устойчиво | Нагрузочный тест 30 мин |
| Входящие события | 500 событий/с устойчиво | Нагрузочный тест 30 мин |
| Пиковая нагрузка | 2 000 событий/с 15 мин | Без потери событий и data corruption |
| API latency | p95 <= 300 мс (простые запросы) | Внутренняя latency до accepted, без внешних webhook |
| Время до webhook-вызова | p95 <= 3 с при здоровом endpoint | От COMMIT сообщения до начала первого HTTP POST |
| Доступность Bot API | >= 99,9% календарного месяца | Серверная availability, исключения определить отдельно |
| Хранение pending updates | 72 ч | TTL/update expiry проверяется тестом |
| RPO событий | 0 подтверждённых транзакций при одиночном отказе worker | Тест инъекции сбоев |

Сроки восстановления, RTO/RPO БД, резервное копирование, межрегиональность, бюджет, местоположение данных, анти-DDoS и поддержка высокой доступности определяются эксплуатационной архитектурой мессенджера. Нельзя обещать RPO=0 для полного регионального отказа без синхронной репликации и подтверждённого решения.

## 19. Мониторинг и операционное управление

Обязательные метрики: bot_api_requests_total{method,status}; request_duration_p95/p99; bot_updates_created; webhook_delivery_attempts{status_class}; webhook_retry_count; oldest_pending_update_age; queue_depth; events_expired; poll_active; idempotency_replay_count; hosted_invocations{result}; hosted_cpu_seconds; hosted_memory_peak; E2EE_DENIED_count. Кардинальность метрик ограничивать — bot_id по возможности в логи/трассы, но не во все Prometheus labels.

Distributed tracing: `request_id` (API), `trace_id` (сквозной трассировки), `event_id` и `message_id` используются для корреляции. Логи редактируют токены, body при наличии PII и ключи. Dashboard платформы показывает здоровье broker, DLQ, долг очереди и внешние timeout. Developer Portal отображает только разрешённую конкретному владельцу статистику, не раскрывая персональные данные участников.

## 21. Порядок реализации и зависимости

**Спринт/пакет A: фундамент.** Аудит имеющихся Identity, Messaging и Chat ACL, создание bot identity, Registry, auth, scopes, единого сообщения через Messaging Service, transactional outbox.

**Пакет B: события.** Router, durable update log, webhook, polling, ретраи, idempotency, мониторинг.

**Пакет C: UX-функции.** Команды, inline-кнопки, callback lifecycle, файлы и media pipeline, групповые разрешения, блокировки, privacy mode.

**Пакет D: hosted.** Изолированный build/deploy, artifact registry, sandbox runtime, secrets broker, quotas, logs, rollback, переключение external/hosted.

**Пакет E: hardening.** Pentest/SSRF, проверка multi-tenancy, нагрузочные испытания, инструкции для разработчиков, OpenAPI/AsyncAPI, runbooks, disaster-recovery drills.

Пакеты могут идти параллельно при наличии отдельных команд. Hosted runtime является самостоятельным крупным блоком безопасности; вводить его в production до изоляционных тестов нельзя.

## 23. Критерии готовности / Definition of Done

ТЗ считается выполненным, когда все требования P0 проходят тесты, оба режима исполнения действительно работают, webhook и polling работают по одной согласованной семантике событий, внешние и hosted боты имеют одинаковую модель прав и API, содержимое E2EE недоступно обычной платформе ботов, выполнены тесты доставки/идемпотентности/SSRF/изоляции, предоставлены миграции и спецификации, показатели нагрузочного профиля достигнуты на утверждённом стенде, а аварийный откат проверен на практике.

### 23.1. Требующие финального согласования параметры

- Базовый стек backend, текущие IDs и структура таблиц, границы существующих сервисов.
- Выбранные значения нагрузки, max sizes, retention, SLO, объём хранения и регионы.
- Конкретный hosted-runtime (Node.js/WASM), упаковка артефактов, sandbox (microVM либо доказуемая альтернатива).
- Политика lifetime токенов, quota plans, ограничения внешнего egress.
- Стратегия существующей E2EE-криптографии и явно допустимые типы чатов для ботов.
- Формальная политика модерации, обработки жалоб, удаления личных данных и логирования.
