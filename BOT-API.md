# Bot API Волны — команды, кнопки и webhook

Публичная инструкция для разработчиков доступна на сайте по адресу `/developers/bots` (ссылка «Разработчикам» на главной).

Реализован фундамент из пакета A ТЗ и получение событий через long polling или webhook: отдельные аккаунты ботов, реестр, токены/scopes, единый Messaging Service, транзакционный outbox, устойчивая очередь событий, личные диалоги и ограниченные разрешения групп. Этот этап предназначен для **внешних текстовых ботов**.

Медиа, локализованные подсказки команд, роли maintainer/viewer и изолированный hosted runtime пока не реализованы. Полное ТЗ в `bot_platform_spec.md` и исходный draft OpenAPI описывают также эти следующие этапы; они не являются перечнем уже работающих методов.

## Обновление существующего PostgreSQL-сервера

Сохраните текущую папку, `.env`, имя Compose-проекта и тома. После получения этой ветки:

```sh
sh scripts/update.sh
```

Скрипт создаёт резервную копию PostgreSQL/файлов, собирает сервер и Web и проверяет сервисы. **Повторный перенос SQLite не нужен.** Схема ботов добавляется при запуске, существующие данные не сбрасываются.

Управление выполняется в личном чате с **главным ботом Волны**. В Web: **Настройки → Мои боты** открывает этот чат с подсказкой команд. В Android и установленном Windows-клиенте найдите `@volna_botfather`, откройте диалог и отправьте `/start`. Пересборка Android для текстовых команд не нужна. Если username уже принадлежал существующему аккаунту, сервер не забирает его: служебный бот получает уникальный username, который возвращает `POST /api/bots/manager {}` и использует Web.

## Создать и запустить бота

1. Отправьте главному боту `/newbot`, затем название и уникальный username. Username общий с пользователями, без учёта регистра. `/cancel` отменяет создание; незавершённый диалог истекает через час и переживает перезапуск API.
2. `/mybots` показывает только ваших ботов. `/token @username` перевыпускает токен, `/revoke @username` отзывает его; `/pause` и `/resume` отключают и включают бота. `/setname @username Название` и `/setdescription @username Описание` меняют настройки.
3. `/groups @username on|off` управляет scope полного чтения групп и **перевыпускает токен**. Администратор конкретной группы отдельно выдаёт grant. `/help` показывает все команды.
4. Секрет отправляется в личный чат владельца и сохраняется в истории сообщений и её резервных копиях. В таблице credentials хранится только SHA-256; журнал аудита секретов не содержит. Старый токен при перевыпуске сразу отзывается. Не пересылайте сообщения с токенами. Главный бот не имеет внешнего API-токена; права проверяются по реальному отправителю сообщения. Команды в группах не исполняются. Изменённые или удалённые до обработки сообщения пропускаются. Создание/изменение, ответ и отметка outbox фиксируются одной транзакцией, повторная обработка не повторяет действие.
5. Запустите пример на своём компьютере или отдельном сервере, задав секрет через окружение:

```sh
export VOLNA_URL=https://ваш-домен
read -r -s -p 'Bot token: ' BOT_TOKEN; export BOT_TOKEN; printf '\n'
export BOT_OFFSET_PATH=./echo-offset.json
python3 examples/echo-bot.py
```

Команды ввода секрета приведены для Bash. Напишите боту `/start`: пример ответит тем же текстом. Он сохраняет offset и использует стабильный Idempotency-Key, чтобы не дублировать ответ после обрыва связи. Не запускайте два процесса polling для одного бота. Не меняйте токен на другого бота, сохраняя offset старого: у каждого свой счётчик событий.

## Адреса и авторизация

Канонические пути: `/bot/v1` и `/developer/v1`. Поддерживаются идентичные `/api/bot/v1` и `/api/developer/v1` для совместимости с установленными прокси. Новый nginx проксирует все четыре пути. Примеры ниже используют `/api`.

Bot API принимает `Authorization: Bearer <bot_token>`. Developer API требует обычный пользовательский access token, полученный после входа. Bot token не предоставляет доступ к пользовательскому API, Developer API, чужим ботам или аккаунту владельца. Токен пользователя не принимается как токен бота. Через интернет используйте HTTPS.

Ответ ошибки Bot/Developer API:

```json
{"error":{"code":"CHAT_ACCESS_DENIED","message":"Чат недоступен","request_id":"…","retryable":false}}
```

Тот же ID есть в `X-Request-ID`. Пользовательские `/api/bots` и `/api/chats` сохраняют прежний формат ошибок для совместимости. Тело запроса Bot/Developer API ограничено 128 КиБ; лимиты отдельных полей проверяются дополнительно.

## Developer API

| Метод | Путь после `/api/developer/v1` | Результат |
|---|---|---|
| POST | `/bots` | Создать: `username`, `display_name`, `description?`, `scopes?`; 201 с bot/token/token_id |
| GET | `/bots` | Только свои боты; исходные токены отсутствуют |
| GET | `/bots/{id}` | Метаданные своего бота |
| PATCH | `/bots/{id}` | `display_name?`, `description?`, `status?` |
| POST | `/bots/{id}/tokens` | `{scopes?: [...]}`; 201 с новым токеном, старые отзываются |
| GET | `/bots/{id}/tokens` | ID, scopes, время выпуска/отзыва; без секрета и хеша |
| DELETE | `/bots/{id}/tokens/{token_id}` | Отозвать токен; 204 |
| GET | `/bots/{id}/audit` | Последние 100 действий без секретов |

Статусы: active, suspended, deleted. Удаление окончательное, username остаётся зарезервированным, история сообщений сохраняется; токены и grants отзываются. Ограничение: 20 неудалённых ботов на владельца. Username — 4–32 символа по общим правилам Волны; название — 1–128, описание — до 1000 символов. Метаданные имени/описания меняются без изменения account_id.

Доступные scopes: `messages:send`, `messages:edit_own`, `messages:delete_own`, `messages:read_events`, `chats:read_basic`, `commands:manage`, `callbacks:answer`, `groups:read_all`. По умолчанию выдаются первые семь. `groups:read_all` включается явно. Токен проверяется повторно после асинхронного чтения тела запроса, а при long polling — перед выдачей событий.

## Bot API

| Метод | Путь после `/api/bot/v1` | Результат |
|---|---|---|
| GET | `/me` | Идентичность бота |
| POST | `/messages` | Отправить текст в разрешённый чат; 201 accepted |
| PATCH | `/messages/{id}` | Изменить своё сообщение: `revision`, `text`; 200 |
| DELETE | `/messages/{id}` | Удалить своё сообщение; 204, повтор безопасен |
| GET | `/chats/{id}` | Тип, режим шифрования, эффективные разрешения |
| GET | `/updates?offset=1&limit=100&timeout=30` | Получить события |
| GET/PUT | `/commands` | Прочитать/заменить `{commands:[{command,description}]}` |

Для отправки:

```http
POST /api/bot/v1/messages
Authorization: Bearer <bot_token>
Idempotency-Key: 40d5cb39-4987-42d9-b3eb-a28106515698
Content-Type: application/json

{"chat_id":"123","type":"text","text":"Привет!","reply_to_message_id":null}
```

Текст: 1–4000 символов, согласно текущему Messaging Service Волны. В сообщениях и событиях id/chat_id/sender_id возвращаются строками; update_id/revision — безопасными целыми числами. Поле account_id в метаданных сохраняет числовой ID аккаунта существующего API Волны. 201 означает сохранение/принятие к доставке, а не прочтение получателем. Сообщения идут через тот же сервис, SSE и push, что и сообщения людей; бот не пишет в messages в обход сервиса.

Idempotency-Key обязателен: 16–128 ASCII-символов `A-Za-z0-9._:-`. В течение 24 часов тот же ключ/бот/тело возвращает прежний результат, другое тело — 409. Ротация токена не сбрасывает ключи. После истечения окна ответ не гарантирует дедупликацию: не повторяйте давно завершённую отправку. Ответы PATCH содержат увеличенную revision; устаревшая revision даёт 409. Только собственные сообщения и текущий разрешённый чат доступны боту.

Лимиты на экземпляр API: 600 обычных запросов/минуту на бота, 120 запросов polling, 60 отправок и 20 отправок в конкретный чат. Есть общий лимит по адресу клиента. При превышении — 429 и Retry-After. Отправки, запрещённые текущей ролью, блокировкой чата, администратором или grant, отклоняются независимо от token scope.

## События и подтверждение

Формат:

```json
{"updates":[{"update_id":1,"event_id":"evt_42","event_type":"message.created","api_version":"1","bot_id":"…","occurred_at":"2026-10-17T00:00:00.000Z","chat_id":"123","chat_sequence":42,"data":{"id":"456","chat_id":"123","sender_id":"789","text":"/start","reply_to_message_id":null,"revision":0,"created_at":"2026-10-17T00:00:00.000Z"}}]}
```

События этого этапа: message.created, message.edited, message.deleted. Сообщения ботов не порождают события для других ботов. Транзакционный PostgreSQL trigger сохраняет outbox при записи сообщения; откат сообщения откатывает и событие. Router формирует устойчивый журнал с монотонным update_id на бота. Повторная обработка outbox не создаёт второй event_id. Новые grants не предоставляют доступ к прежней истории.

`offset=N` подтверждает события с ID меньше N. Сначала обработайте события и сохраните локальное состояние, затем запрашивайте следующий ID. Без подтверждения событие может прийти повторно — обработчик обязан быть идемпотентным. limit — 1–100, timeout — 0–30 секунд. Отрицательные, дробные и будущие offset отклоняются. Второй активный poll получает 409; при падении процесса lease истекает через 35 секунд. Необработанные события сохраняются 24 часа после формирования update. Права и версия grant повторно проверяются перед выдачей; смена доступа/блокировка исключают прежние ожидающие события.

## Пользовательские и групповые права

- `POST /api/bots/manager {}` — открыть личный чат с главным ботом, вернуть `id`, `bot_id`, `username` и приветствие при первом открытии. Требует пользовательскую сессию.\n- `POST /api/bots/{id}/start {}` — явно запустить/разблокировать личный диалог.
- `POST /api/bots/{id}/block {}` — прекратить новые доступные события и запретить отправку бота. Простое открытие прежнего диалога не снимает блокировку.
- `GET /api/bots/resolve?username=name` — найти активного бота по username.
- `GET /api/chats/{chat_id}/bots` — участникам доступны боты и выданные им разрешения.
- `PUT /api/chats/{chat_id}/bots/{id} {"visibility":"restricted","can_send":true}` — администратор основной группы добавляет бота и выдаёт grant.
- `DELETE /api/chats/{chat_id}/bots/{id}` — администратор отзывает grant и удаляет участника.

В Web меню группы «Боты и доступ» показывает эти права всем участникам; изменять их могут только owner/admin. В restricted режиме передаются slash-команды без адресата или с адресом этого бота, точные `@username` и ответы на сообщения этого бота. Полный доступ требует **одновременно** `full_read` от администратора и `groups:read_all` в токене. Добавление участника обычным старым API само по себе не выдаёт grant. В этом этапе grant и события относятся к основной группе; темы/подгруппы не наследуют доступ к событиям автоматически.

Каждый чат имеет encryption_mode server_readable/e2ee. Для e2ee запрещены bot membership и выдача plaintext-событий. Прозрачное переключение режима запрещено триггером БД. Это архитектурная граница для ботов, а не реализация клиентского E2EE-протокола.


## Inline-кнопки и меню команд (0.12.60)

Бот может передать клавиатуру при отправке текста:

```json
{"chat_id":"123","type":"text","text":"Выберите действие","reply_markup":{"inline_keyboard":[[{"text":"Каталог","callback_data":"catalog"},{"text":"Помощь","callback_data":"help"}]]}}
```

До 8 строк по 8 кнопок; подпись 1–64 Unicode code points, callback_data 1–128 байт UTF-8; NUL и непарные суррогаты отклоняются с 400. В этом этапе поддерживаются только callback-кнопки, URL-кнопок нет. Новое поле входит в проверку Idempotency-Key. Запросы прежних версий без reply_markup сохраняют прежний fingerprint.

PATCH /bot/v1/messages/{id} принимает revision и text и/или reply_markup. null либо {"inline_keyboard":[]} удаляет клавиатуру. Изменение только клавиатуры также повышает revision. При замене клавиатуры старые button_id становятся недействительными; изменение текста без reply_markup сохраняет кнопки.

В пользовательских сообщениях поле bot_buttons содержит только строки кнопок {id,text}; callback_data не передаётся клиенту. Пересылка не копирует действия. Кнопки удалённого сообщения недоступны.

Клиент:
- POST /api/bots/interactions с {message_id,button_id,interaction_id}, где interaction_id — уникальный ID физического нажатия (16–128 символов, как Idempotency-Key).
- Повтор того же нажатия возвращает прежний callback_id. Повтор nonce с другим действием даёт 409. actor_id, bot_id и callback_data передавать нельзя.
- GET /api/bots/interactions/{callback_id} доступен только нажавшему пользователю. Ответ status=pending|answered|expired, expires_at и, после ответа, answer:{text,show_alert}. Клиенты опрашивают статус с интервалом 2 секунды, до 120 секунд.
- Членство, история, режим шифрования, блокировка, активность кнопки/бота и версия grant проверяются при создании, выдаче события и ответе.

Боту приходит callback.created через тот же durable polling log. data содержит callback_id, message_id, button_id, actor:{id,username,display_name}, data (сохранённый callback_data), expires_at. Телефон/сессия пользователя не выдаются.

POST /bot/v1/callbacks/{callback_id}/answer {text?,show_alert?} требует callbacks:answer. text до 200 Unicode code points; show_alert boolean. Срок ответа — 120 секунд. Возвращает 204; повтор идентичного ответа безопасен, другой ответ — 409; истёкший callback — 410. Чужие callback не доступны. Ответ сохраняется для пользовательского опроса и отправляется по SSE только нажавшему пользователю.

Новые токены включают callbacks:answer по умолчанию. Старые токены автоматически не расширяются: владелец включает scope через главного бота командой /callbacks @username on (с перевыпуском токена) или явно задаёт scopes в Developer API.

GET /api/chats/{chat_id}/bot-commands возвращает команды доступных в чате ботов. Web и Android показывают меню и подставляют выбранную команду в поле ввода. Пользователь отправляет её обычным сообщением. В группе добавляется @username нужного бота. Обновления PUT /bot/v1/commands рассылают уведомление Web; Android обновляет список каждые 30 секунд и при открытии меню.

У главного бота есть кнопки «Создать бота», «Мои боты», «Помощь» и меню всех его команд. Действия проверяют владельца по авторизованному нажавшему пользователю.

Для отображения кнопок и меню в Android требуется APK 0.12.60. Из прежней папки установки запустите sh scripts/build-android.sh: скрипт использует существующий ключ подписи, публикует APK и обновляет сервер. Старая версия Android продолжает работать с текстовыми сообщениями и ручными командами.


## Проверки и эксплуатация

Продолжайте использовать один API-процесс: основной сервер пока сохраняет синхронный PostgreSQL-драйвер и локальное realtime-состояние. Outbox/updates/idempotency/audit находятся в PostgreSQL и попадают в обычную резервную копию.

```sh
# На отдельной тестовой PostgreSQL, с pg_dump 17 в PATH:
VOLNA_TEST_DATABASE_URL=postgresql://... npm test
VOLNA_TEST_DATABASE_URL=postgresql://... node tests/bot-ui.mjs
npm run build --prefix client
```

Браузерная проверка требует зависимости client и Chromium. Тесты проверяют настоящую БД, SSE, восстановление outbox после перезапуска, scopes/права групп, блокировку, ротацию и отзыв токенов, revision и идемпотентность. Hosted-код не загружается и не исполняется внутри основного сервера.

В [GitHub Actions](https://github.com/andluk87/volna/actions/runs/39004956441) прошли **196 серверных тестов**, сборка Web и браузерный сценарий: управление главным ботом, меню команд, callback-кнопки, alert-ответ, права группы, мобильная вёрстка и контраст текста. Android unit/UI-тесты и сборка APK также проверены с подготовленными emoji-ресурсами штатной сборки. CI APK собран с тестовым доменом и не публикуется как обновление рабочей установки; рабочий APK собирается штатным скриптом с её API URL и ключом подписи.

Исправлена выявленная при прогоне редкая гонка синхронного PostgreSQL-worker: ответы сопоставляются с ID запроса, запоздалое уведомление не подменяет ответ следующей операции. Регрессионный тест воспроизводит запоздалые уведомления и проверяет смешанные exec/select операции. Все данные проверок синтетические; рабочий сервер владельца не изменялся.

Существующий `npm run test:render` сейчас останавливается на ожидании «Внешний вид». То же падение воспроизведено на исходной ветке PostgreSQL до изменений Bot API: SSR-fixture не проходит существующий этап ожидания облачного оформления. Этот старый smoke-тест не изменён; новый интерфейс проверен браузером с реальным PostgreSQL.

## Webhook — 0.12.61

Настройка через личный чат главного бота:

```
/webhook @my_bot https://bot.example.com/events
/webhook @my_bot status
/webhook @my_bot off
```

Главный бот асинхронно проверяет DNS через отдельный egress-сервис. После успешной проверки включает webhook, прерывает активный polling с `409 DELIVERY_MODE_CONFLICT` и присылает одноразовую ссылку на отдельный случайный секрет подписи. Ссылка действует 5 минут; откройте её и нажмите «Показать секрет». Сам секрет в истории чата не сохраняется. Ссылка предоставляет доступ предъявителю, поэтому не пересылайте её. URL-фрагмент не передаётся в HTTP access logs; предпросмотр страницы не расходует ссылку. Повторная установка URL меняет секрет и аннулирует старую ссылку; `status` секрет не возвращает. Пока новый URL проверяется, доступен polling; `off` отменяет в том числе незавершённую проверку. Чужими ботами управлять нельзя.

Программно (нужен `messages:read_events`):

- `PUT /bot/v1/delivery/webhook {"url":"https://bot.example.com/events","event_types":["message.created","callback.created"]}` → `{mode:"webhook",webhook_secret:"..."}`. URL проверяется до активации; секрет показывается в этом ответе один раз.
- `DELETE /bot/v1/delivery/webhook` → 204, включает polling.
- `GET /bot/v1/delivery/status` → режим, URL, подписки, количество ожидающих событий, последние HTTP-код/безопасная категория ошибки, счётчик ошибок и до 10 записей о попытках без содержимого сообщений. `finished=0`: ожидает; `1`: доставлено; `2`: срок события истёк.

Если `event_types` отсутствует, подписка включает `message.created`, `message.edited`, `message.deleted`, `callback.created`. Другие типы остаются в общем журнале до TTL; после выключения webhook их можно забрать polling. Установка webhook через главного бота подписывает на все четыре типа.

POST содержит неизменный JSON одного update, `Content-Type: application/json`, `X-Bot-Event-Id`, `X-Bot-Timestamp` (Unix seconds), `X-Bot-Signature: sha256=<hex>`. Считайте подпись **до JSON parse**:

```python
import hashlib, hmac, time

def verify(secret, timestamp, raw_body, signature):
    if abs(time.time() - int(timestamp)) > 300:
        return False
    expected = 'sha256=' + hmac.new(
        secret.encode(), timestamp.encode() + b'.' + raw_body, hashlib.sha256
    ).hexdigest()
    return hmac.compare_digest(expected, signature)
```

Получатель должен также сохранять обработанные `event_id` для защиты от повторного выполнения. Верните 2xx после надёжного сохранения события. Бюджет запроса — 5 секунд включая DNS/TLS и чтение ответа; ответ ограничен 8 KiB. Все не-2xx, редиректы, timeout и сетевые ошибки повторяются с тем же `event_id` и raw body, новым timestamp/подписью. Доставка at-least-once, порядок после retry не гарантирован. Задержки: экспоненциально от 1 секунды с jitter ±25%, после пяти ошибок circuit breaker минимум около 45 секунд, максимум около 375 секунд. TTL сообщений 24 часа, callbacks 120 секунд. Диагностика попыток хранится 7 дней без payload; истёкшие события не отправляются. У одного бота одновременно один запрос, глобально максимум четыре; расписание сохраняется в PostgreSQL. Поддерживается один процесс API, как и у polling.

Очередь создаётся независимо от HTTP отправки пользователем. Перед каждой попыткой повторяются проверки статуса бота/владельца, действующего токена/scopes, chat grant/version, членства и callback. Отозванный токен или приостановленный бот останавливает отправку; доступ к старому отозванному grant не восстанавливается. Уже начавшийся сетевой запрос может завершиться после переключения транспорта или отзыва доступа; его поздний результат не подтверждает событие в новой конфигурации.

### Сервис доставки и обновление

`compose.yaml` автоматически запускает `webhook-egress`; `scripts/update.sh` собирает его и проверяет готовность. У сервиса **только отдельная bridge-сеть**, нет сети приложения/БД, переменных credentials, uploads или Docker socket. API передаёт ровно URL, подписанный payload и заголовки через Unix socket в отдельном общем томе. В HTTP webhook никогда не передаётся bot token или ключ шифрования.

Перед запуском Node сервис устанавливает IPv4/IPv6 OUTPUT deny policy: только публичный TCP 443 и встроенный DNS Docker. Приватные/специальные диапазоны запрещены firewall. Затем UID/GID меняются на 1000 и все capabilities сбрасываются. Root filesystem read-only, CPU/RAM/PID ограничены. Невозможность установить firewall останавливает сервис. Для запуска нужны rootful Docker и поддержка iptables/ip6tables; rootless Docker потребует эквивалентного внешнего сетевого фильтра. Проверка: `sh scripts/test-webhook-egress.sh` (отдельный временный Compose project).

HTTPS обязателен, только порт 443; credentials в URL и redirects запрещены, TLS проверяется. Каждый DNS resolve проверяет **все** полученные IP, соединение привязано к проверенному IP с сохранением hostname/SNI. IPv4-mapped, NAT64/6to4, локальные, multicast, reserved и documentation ranges запрещены. Ответы/запросы endpoint в логи не пишутся.

Одноразовая выдача через `GET /bot/v1/delivery/secret` и `POST /bot/v1/delivery/secret/claim {ticket}` использует отдельную 256-битную capability, выданную только в личный чат владельца. Этот маршрут не требует bot token; capability разрешает только однократное чтение секрета текущей конфигурации, не управление ботом. В БД хранится только SHA-256 capability; конкурентные предъявления сериализованы, повтор/expiry/off/смена URL → 410. Страница имеет no-store/CSP/no-referrer, не загружает внешние ресурсы и удаляет ticket из адресной строки. Секреты в БД зашифрованы AES-256-GCM; ключ `/data/bot-webhook.key` создаётся с правами 0600 в постоянном томе. Полный backup через скрипт и backup админ-панели включают этот ключ. При восстановлении БД **нужно восстановить соответствующий ключ** рядом с uploads или по `WEBHOOK_KEY_PATH`; без него существующие webhook нужно перенастроить. Ключ не помещается в egress-контейнер. Для запуска API вне Compose настройте `WEBHOOK_EGRESS_SOCKET` и при необходимости `WEBHOOK_KEY_PATH`; без egress настройка возвращает 503.

Сборка Android не нужна: клиент 0.12.60 уже поддерживает команды главного бота.
