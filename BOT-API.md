# Bot API Волны — первый этап

Реализован фундамент из пакета A ТЗ и получение событий через long polling: отдельные аккаунты ботов, реестр, токены/scopes, единый Messaging Service, транзакционный outbox, устойчивая очередь событий, личные диалоги и ограниченные разрешения групп. Этот этап предназначен для **внешних текстовых ботов**.

Webhook, медиа, inline-кнопки/callback, локализованные подсказки команд, роли maintainer/viewer и изолированный hosted runtime пока не реализованы. Полное ТЗ в `bot_platform_spec.md` и исходный draft OpenAPI описывают также эти следующие этапы; они не являются перечнем уже работающих методов.

## Обновление существующего PostgreSQL-сервера

Сохраните текущую папку, `.env`, имя Compose-проекта и тома. После получения этой ветки:

```sh
sh scripts/update.sh
```

Скрипт создаёт резервную копию PostgreSQL/файлов, собирает сервер и Web и проверяет сервисы. **Повторный перенос SQLite не нужен.** Схема ботов добавляется при запуске, существующие данные не сбрасываются.

Управление выполняется в личном чате с **главным ботом Волны**. В Web: **Настройки → Мои боты** открывает этот чат с подсказкой команд. В Android и установленном Windows-клиенте найдите `@volna_botfather`, откройте диалог и отправьте `/start`. Пересборка Android для текстовых команд не нужна. Если username уже принадлежал существующему аккаунту, сервер не забирает его: служебный бот получает уникальный username, который возвращает `POST /api/bots/manager {}` и использует Web.

## Создать и запустить бота

1. Отправьте главному боту `/newbot`, затем название и уникальный username. Username общий с пользователями, без учёта регистра. `/cancel` отменяет создание; незавершённый диалог истекает через час и переживает перезапуск API.
2. `/mybots` показывает только ваших ботов. `/token @username` перевыпускает токен, `/revoke @username` отзывает его; `/pause` и `/resume` отключают и включают бота. `/setname @username Название` и `/setdescription @username Описание` меняют настройки.
3. `/groups @username on|off` управляет scope полного чтения групп и **перевыпускает токен**. Администратор конкретной группы отдельно выдаёт grant. `/help` показывает все команды.
4. Секрет отправляется в личный чат владельца и сохраняется в истории сообщений и её резервных копиях. В таблице credentials хранится только SHA-256; журнал аудита секретов не содержит. Старый токен при перевыпуске сразу отзывается. Не пересылайте сообщения с токенами. Главный бот не имеет внешнего API-токена; права проверяются по реальному отправителю сообщения. Команды в группах не исполняются. Изменённые или удалённые до обработки сообщения пропускаются. Создание/изменение, ответ и отметка outbox фиксируются одной транзакцией, повторная обработка не повторяет действие.
5. Запустите пример на своём компьютере или отдельном сервере, задав секрет через окружение:

```sh
export VOLNA_URL=https://ваш-домен
read -r -s -p 'Bot token: ' BOT_TOKEN; export BOT_TOKEN; printf '\n'
export BOT_OFFSET_PATH=./echo-offset.json
python3 examples/echo-bot.py
```

Команды ввода секрета приведены для Bash. Напишите боту `/start`: пример ответит тем же текстом. Он сохраняет offset и использует стабильный Idempotency-Key, чтобы не дублировать ответ после обрыва связи. Не запускайте два процесса polling для одного бота. Не меняйте токен на другого бота, сохраняя offset старого: у каждого свой счётчик событий.

## Адреса и авторизация

Канонические пути: `/bot/v1` и `/developer/v1`. Поддерживаются идентичные `/api/bot/v1` и `/api/developer/v1` для совместимости с установленными прокси. Новый nginx проксирует все четыре пути. Примеры ниже используют `/api`.

Bot API принимает `Authorization: Bearer <bot_token>`. Developer API требует обычный пользовательский access token, полученный после входа. Bot token не предоставляет доступ к пользовательскому API, Developer API, чужим ботам или аккаунту владельца. Токен пользователя не принимается как токен бота. Через интернет используйте HTTPS.

Ответ ошибки Bot/Developer API:

```json
{"error":{"code":"CHAT_ACCESS_DENIED","message":"Чат недоступен","request_id":"…","retryable":false}}
```

Тот же ID есть в `X-Request-ID`. Пользовательские `/api/bots` и `/api/chats` сохраняют прежний формат ошибок для совместимости. Тело запроса Bot/Developer API ограничено 128 КиБ; лимиты отдельных полей проверяются дополнительно.

## Developer API

| Метод | Путь после `/api/developer/v1` | Результат |
|---|---|---|
| POST | `/bots` | Создать: `username`, `display_name`, `description?`, `scopes?`; 201 с bot/token/token_id |
| GET | `/bots` | Только свои боты; исходные токены отсутствуют |
| GET | `/bots/{id}` | Метаданные своего бота |
| PATCH | `/bots/{id}` | `display_name?`, `description?`, `status?` |
| POST | `/bots/{id}/tokens` | `{scopes?: [...]}`; 201 с новым токеном, старые отзываются |
| GET | `/bots/{id}/tokens` | ID, scopes, время выпуска/отзыва; без секрета и хеша |
| DELETE | `/bots/{id}/tokens/{token_id}` | Отозвать токен; 204 |
| GET | `/bots/{id}/audit` | Последние 100 действий без секретов |

Статусы: active, suspended, deleted. Удаление окончательное, username остаётся зарезервированным, история сообщений сохраняется; токены и grants отзываются. Ограничение: 20 неудалённых ботов на владельца. Username — 4–32 символа по общим правилам Волны; название — 1–128, описание — до 1000 символов. Метаданные имени/описания меняются без изменения account_id.

Доступные scopes: `messages:send`, `messages:edit_own`, `messages:delete_own`, `messages:read_events`, `chats:read_basic`, `commands:manage`, `groups:read_all`. По умолчанию выдаются первые шесть. `groups:read_all` включается явно. Токен проверяется повторно после асинхронного чтения тела запроса, а при long polling — перед выдачей событий.

## Bot API

| Метод | Путь после `/api/bot/v1` | Результат |
|---|---|---|
| GET | `/me` | Идентичность бота |
| POST | `/messages` | Отправить текст в разрешённый чат; 201 accepted |
| PATCH | `/messages/{id}` | Изменить своё сообщение: `revision`, `text`; 200 |
| DELETE | `/messages/{id}` | Удалить своё сообщение; 204, повтор безопасен |
| GET | `/chats/{id}` | Тип, режим шифрования, эффективные разрешения |
| GET | `/updates?offset=1&limit=100&timeout=30` | Получить события |
| GET/PUT | `/commands` | Прочитать/заменить `{commands:[{command,description}]}` |

Для отправки:

```http
POST /api/bot/v1/messages
Authorization: Bearer <bot_token>
Idempotency-Key: 40d5cb39-4987-42d9-b3eb-a28106515698
Content-Type: application/json

{"chat_id":"123","type":"text","text":"Привет!","reply_to_message_id":null}
```

Текст: 1–4000 символов, согласно текущему Messaging Service Волны. В сообщениях и событиях id/chat_id/sender_id возвращаются строками; update_id/revision — безопасными целыми числами. Поле account_id в метаданных сохраняет числовой ID аккаунта существующего API Волны. 201 означает сохранение/принятие к доставке, а не прочтение получателем. Сообщения идут через тот же сервис, SSE и push, что и сообщения людей; бот не пишет в messages в обход сервиса.

Idempotency-Key обязателен: 16–128 ASCII-символов `A-Za-z0-9._:-`. В течение 24 часов тот же ключ/бот/тело возвращает прежний результат, другое тело — 409. Ротация токена не сбрасывает ключи. После истечения окна ответ не гарантирует дедупликацию: не повторяйте давно завершённую отправку. Ответы PATCH содержат увеличенную revision; устаревшая revision даёт 409. Только собственные сообщения и текущий разрешённый чат доступны боту.

Лимиты на экземпляр API: 600 обычных запросов/минуту на бота, 120 запросов polling, 60 отправок и 20 отправок в конкретный чат. Есть общий лимит по адресу клиента. При превышении — 429 и Retry-After. Отправки, запрещённые текущей ролью, блокировкой чата, администратором или grant, отклоняются независимо от token scope.

## События и подтверждение

Формат:

```json
{"updates":[{"update_id":1,"event_id":"evt_42","event_type":"message.created","api_version":"1","bot_id":"…","occurred_at":"2026-10-17T00:00:00.000Z","chat_id":"123","chat_sequence":42,"data":{"id":"456","chat_id":"123","sender_id":"789","text":"/start","reply_to_message_id":null,"revision":0,"created_at":"2026-10-17T00:00:00.000Z"}}]}
```

События этого этапа: message.created, message.edited, message.deleted. Сообщения ботов не порождают события для других ботов. Транзакционный PostgreSQL trigger сохраняет outbox при записи сообщения; откат сообщения откатывает и событие. Router формирует устойчивый журнал с монотонным update_id на бота. Повторная обработка outbox не создаёт второй event_id. Новые grants не предоставляют доступ к прежней истории.

`offset=N` подтверждает события с ID меньше N. Сначала обработайте события и сохраните локальное состояние, затем запрашивайте следующий ID. Без подтверждения событие может прийти повторно — обработчик обязан быть идемпотентным. limit — 1–100, timeout — 0–30 секунд. Отрицательные, дробные и будущие offset отклоняются. Второй активный poll получает 409; при падении процесса lease истекает через 35 секунд. Необработанные события сохраняются 24 часа после формирования update. Права и версия grant повторно проверяются перед выдачей; смена доступа/блокировка исключают прежние ожидающие события.

## Пользовательские и групповые права

- `POST /api/bots/manager {}` — открыть личный чат с главным ботом, вернуть `id`, `bot_id`, `username` и приветствие при первом открытии. Требует пользовательскую сессию.\n- `POST /api/bots/{id}/start {}` — явно запустить/разблокировать личный диалог.
- `POST /api/bots/{id}/block {}` — прекратить новые доступные события и запретить отправку бота. Простое открытие прежнего диалога не снимает блокировку.
- `GET /api/bots/resolve?username=name` — найти активного бота по username.
- `GET /api/chats/{chat_id}/bots` — участникам доступны боты и выданные им разрешения.
- `PUT /api/chats/{chat_id}/bots/{id} {"visibility":"restricted","can_send":true}` — администратор основной группы добавляет бота и выдаёт grant.
- `DELETE /api/chats/{chat_id}/bots/{id}` — администратор отзывает grant и удаляет участника.

В Web меню группы «Боты и доступ» показывает эти права всем участникам; изменять их могут только owner/admin. В restricted режиме передаются slash-команды без адресата или с адресом этого бота, точные `@username` и ответы на сообщения этого бота. Полный доступ требует **одновременно** `full_read` от администратора и `groups:read_all` в токене. Добавление участника обычным старым API само по себе не выдаёт grant. В этом этапе grant и события относятся к основной группе; темы/подгруппы не наследуют доступ к событиям автоматически.

Каждый чат имеет encryption_mode server_readable/e2ee. Для e2ee запрещены bot membership и выдача plaintext-событий. Прозрачное переключение режима запрещено триггером БД. Это архитектурная граница для ботов, а не реализация клиентского E2EE-протокола.

## Проверки и эксплуатация

Продолжайте использовать один API-процесс: основной сервер пока сохраняет синхронный PostgreSQL-драйвер и локальное realtime-состояние. Outbox/updates/idempotency/audit находятся в PostgreSQL и попадают в обычную резервную копию.

```sh
# На отдельной тестовой PostgreSQL, с pg_dump 17 в PATH:
VOLNA_TEST_DATABASE_URL=postgresql://... npm test
VOLNA_TEST_DATABASE_URL=postgresql://... node tests/bot-ui.mjs
npm run build --prefix client
```

Браузерная проверка требует зависимости client и Chromium. Тесты проверяют настоящую БД, SSE, восстановление outbox после перезапуска, scopes/права групп, блокировку, ротацию и отзыв токенов, revision и идемпотентность. Hosted-код не загружается и не исполняется внутри основного сервера.

Проверки главного бота прошли в [GitHub Actions](https://github.com/andluk87/volna/actions/runs/38994110182): **191 тест**, сборка Web и браузерный сценарий создания через чат, смены токена/scopes, pause/resume, прав группы и мобильного диалога. В полном прогоне также проверены резервные копии с PostgreSQL-клиентом 17. Все данные синтетические; рабочий сервер владельца не изменялся. Локальная файловая система окружения зависла на записи, поэтому итоговая проверка выполнена на чистом GitHub runner.

Существующий `npm run test:render` сейчас останавливается на ожидании «Внешний вид». То же падение воспроизведено на исходной ветке PostgreSQL до изменений Bot API: SSR-fixture не проходит существующий этап ожидания облачного оформления. Этот старый smoke-тест не изменён; новый интерфейс проверен браузером с реальным PostgreSQL.
